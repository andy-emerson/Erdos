# Prime Graph: Exact Rationals over a Shared Coprime Base, Specification v0.3

Oct 28, 2026 · Andrew Emerson

v0.3 restates the design of [v0.2](v0.2.md) as a pure specification, and adds [§10 Consistency](#10-consistency). The concepts are explained in the concept paper, in [`../paper/`](../paper/).

## 1. Scope

This specification defines a representation of exact rational numbers whose denominators are factored over one coprime base shared by all values, and the arithmetic, arrays, lifetimes and requirements on it.

In scope: the data model, its invariants, entry of values, factor refinement, arithmetic on values and arrays, consistency, scalability, precision, determinism and errors.

Out of scope: rounding and approximation, programming-language syntax and bindings, input and output formats (except the M1 text form of §8.7), and complex numbers (spec 06).

## 2. Conformance language

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are to be interpreted as described in RFC 2119 when, and only when, they appear in capitals.

A rule marked **(M1)** is an implementation choice of milestone M1: M1 conforms to it, and a later version MAY change it. Unmarked rules are design commitments. Sections or paragraphs marked *non-normative* state no requirement.

## 3. Terms and notation

- **Coprime base.** A finite family $p = (p_1, \ldots, p_k)$ of pairwise coprime integers $p_i > 1$, the **base elements**. The index $i$ is an identifier; identifiers of freed base elements MAY be reused.
- **Atom.** Each base element is stored as $p_i = \prod_j q_j^{e_j}$ over its atoms $q_j > 1$, with atom exponents $e_j \ge 1$. "Atom" is this specification's term for a part of a base element; the concept paper does not use it. Each atom is a proved prime or an **unrefined factor** (an integer not yet known to be prime or composite, treated as prime until refined).
- **Primitive.** A base element is primitive if its atom exponents satisfy $\gcd(e) = 1$.
- **Exponent vector.** A vector $a \in \mathbb{N}^k$, stored sparsely as the pairs $(i, a_i)$ with $a_i > 0$. Its support is $\text{supp}(a) = \{ i : a_i > 0 \}$.
- **Multi-index notation.** $p^{a} = \prod_i p_i^{a_i}$. For exponent vectors $a, b$: $a \vee b$ and $a \wedge b$ are the componentwise maximum and minimum, so $\text{lcm}(p^a, p^b) = p^{a \vee b}$, $\gcd(p^a, p^b) = p^{a \wedge b}$ and $p^a p^b = p^{a+b}$.
- **Factorization over the coprime base.** For a denominator $d$, the exponent vector $a$ with $d = p^a$.
- **Value.** An exact rational $x = m / p^{a}$ with numerator $m \in \mathbb{Z}$, stored in two's complement and carrying the sign. An integer has $a = 0$; zero is $m = 0$, $a = 0$.
- **Holder.** An object that owns a numerator (or none) and a factorization over the coprime base: a value, an array's common denominator, or an array exception (§9.1). M1 also uses transient holders internally during entry (M1). For a holder $h$, $a(h)$ is its exponent vector and $a_i(h)$ its $i$-th component.
- **Handle.** An opaque reference by which a program refers to a value or an array.
- **Holder list.** For base element $p_i$, the list of holders $h$ with $a_i(h) > 0$. Its length is the base element's **reference count**.
- **Freed.** A base element is freed when it is removed from the coprime base and its atoms from the dictionary (§6.2).
- **Dictionary.** A map from each atom to the base element that contains it.
- **Canonical form (reduction to lowest terms).** A value is in canonical form if $\gcd(m, p^a) = 1$ and its factorization stores no zero exponent. Reducing a value means bringing it to canonical form.
- **Factor refinement.** Replacing one base element by two or more pairwise coprime base elements whose powers multiply to it, with every holder's factorization rewritten so that no value changes (§7.3, §7.4).
- **Common-denominator representation.** The array layout of §9.1: one common denominator $D$, dense numerators scaled to $D$, and exceptions.
- **Lazy reduction.** Not reducing intermediate results inside an array expression, and reducing once at its end (§9.4).
- **Array expression.** A sequence of array operations evaluated together under lazy reduction.
- **Aggregate.** An operation combining an array into one value (sum, dot product).
- $v_q(m)$ is the exponent of atom $q$ in $m$ (for an unrefined factor, the largest $t$ with $q^t \mid m$). $\text{sgn}(m) \in \{-1, 0, 1\}$.

## 4. Data model

All values of one context (a **graph**) share one coprime base, one dictionary and one set of holders.

1. **Base elements.** Each base element MUST store its atoms with their exponents, its holder list and its reference count. Each base element MUST be primitive; a base element with one atom is that atom.
2. **Holders.** Each holder MUST store its numerator and its factorization over the coprime base. Each entry $(i, a_i)$ of a factorization MUST record the holder's position in $p_i$'s holder list, so that removal from that list costs $O(1)$. A holder MAY cache $p^a$ as an integer; such a cache is derived data (§10).
3. **Dictionary.** The dictionary MUST map every atom to its base element. It SHOULD be a direct-indexed array for atoms below $2^{16}$ and a hash table above. When a base element is freed, its atoms MUST be removed from the dictionary.
4. **Handles.** A value's handle MUST refer to its holder; a value MUST NOT be stored elsewhere.

## 5. Invariants

The following MUST hold between operations.

- **I1. Coprime base.** All atoms of the graph are pairwise coprime, and each atom belongs to exactly one base element. Hence the base elements are pairwise coprime. Every base element is primitive.
- **I2. Index consistency.** Holder $h$ appears in $p_i$'s holder list exactly when $a_i(h) > 0$, exactly once, at the position its factorization records. Where an exponent is stored in more than one place, all copies are equal (§10).
- **I3. Reference counts.** Each reference count equals the length of its holder list. No base element has an empty holder list: a base element whose count reaches zero is freed.
- **I4. Canonical form.**
  - Every value is in canonical form after every operation that produces it.
  - Every array is in canonical form as a whole (§9.1) whenever it is observable outside an open array expression.
- **I5. Unique values, history-dependent representation.** The rational value of every holder, and the result of every operation, is independent of the coprime base's current refinement and of an array's dense/exception split. The representation itself MAY depend on the history of the graph.

## 6. Lifetimes

1. **Creation.** Creating a value enters its denominator (§7), reduces it (§8.2), and returns a handle.
2. **Release.** Releasing a value removes its holder from the holder list of each base element in its support and decrements those reference counts. Base elements whose count reaches zero MUST be freed (I3). Releasing an array releases its common denominator and each exception in the same way.
3. **Cancellation.** When a result's numerator becomes 0, or an exponent becomes 0, the affected entries MUST be removed from the factorization and from the holder lists, with reference counts decremented as in release.
4. **Results.** Every operation's result is a new object. No operation changes the value of an operand; factor refinement MAY rewrite an operand's factorization.
5. **Destruction.** Destroying a graph frees every value and array still alive in it (M1).
6. **Released handles.** Using a released handle, until its holder is reused, MUST give the invalid-argument status, or a sentinel for sign, is-zero and compare (M1). Releasing a handle twice aborts (M1).

## 7. Entry and factor refinement

### 7.1 Atoms of a new denominator

A new denominator $d > 1$ is decomposed into atoms as follows.

1. **Small primes.**
   1. Powers of 2 MUST be removed in one step by counting trailing zero bits.
   2. Odd primes below $2^{16}$ MUST be tried in ascending order, stopping once $q^2$ exceeds the remaining cofactor. Each divisibility test MUST be a multiplication by a precomputed modular inverse and a comparison, evaluated without branches in blocks of 8. An implementation MAY test a bounded number of primes beyond the stop (M1: the stop is checked once per 32 primes).
   3. Each dividing prime MUST be divided out completely.
2. **Remaining cofactor $r > 1$**, in order:
   1. look $r$ up in the dictionary as a whole; if found, it is that atom;
   2. otherwise $r$ is prime if step 1 stopped early or $r < 2^{32}$;
   3. otherwise trial-divide $r$ by the **bounded list of the 16 most recently seen large primes** (M1: most recent first; every large prime of an entered denominator counts as seen);
   4. otherwise apply a deterministic Miller–Rabin test, exact for 64-bit integers;
   5. if $r$ is composite, it MUST be factored by Pollard's rho method. At 64 bits every atom is therefore a proved prime; unrefined factors arise only beyond 64 bits (M2, §12.1).
3. Correctness MUST NOT depend on the bounded list. Entry MUST NOT test $r$ against every known large prime.
4. An implementation MAY cache the atoms of previously entered denominators in a cache of fixed size, provided the resulting coprime base is the same as without it (M1: 8,192 slots, 2-way sets).

### 7.2 Connecting a denominator

Each atom of $d$ MUST be looked up in the dictionary.

1. Atoms not in the dictionary MUST be combined into **one** new base element, with its atom exponents divided by their gcd. No existing base element is touched by them.
2. Each existing base element containing an atom of $d$ MUST be tested by the ratio-class rule (§7.3), and refined if the rule requires.
3. The factorization of $d$ MUST then be built by dictionary lookups.

### 7.3 Ratio-class refinement

Let base element $p_i$ have atoms $q_1, \ldots, q_s$ with exponents $e_1, \ldots, e_s$, and let $f_j = v_{q_j}(d)$ ($f_j = 0$ if absent). Partition the atoms into **ratio classes** by the value of $f_j / e_j$.

- **One class**, with ratio $\rho$: then $\rho \in \mathbb{N}$, and $d$'s part on these atoms is $p_i^{\rho}$. No refinement takes place; $a_i = \rho$.
- **Several classes** $C_1, \ldots, C_r$: $p_i$ MUST be refined into one base element per class. With $g_t = \gcd\{ e_j : j \in C_t \}$ and $P_t = \prod_{j \in C_t} q_j^{e_j / g_t}$:

$$
p_i = \prod_{t=1}^{r} P_t^{\,g_t}.
$$

**Exponent rule.** Every holder with exponent $w$ on $p_i$ MUST receive exponent $w\, g_t$ on each $P_t$. Its value is unchanged.

Refinement MUST be the least that the rule requires: base elements are not refined further.

*Examples (non-normative).* 30 then 45: ratios 0, 2, 1 on 2, 3, 5, so 30 is refined into 2, 3, 5. 30 then 900: every ratio is 2, so nothing is refined and $a_{30} = 2$. 100 then 35: 100 enters as base element 10 with exponent 2; 35 gives ratios 0 and 1 on 2 and 5, so the base becomes 2, 5, 7.

### 7.4 Copy and loop

To move class $C_t$ out of $p_i$ into a new base element $P_t$:

1. Copy $p_i$'s holder list as $P_t$'s holder list. $p_i$ keeps the remaining atoms, made primitive.
2. Loop once over that list, giving each holder the entry $(P_t, w\, g_t)$ at the same list position, and setting its exponent on the remaining element by the exponent rule.
3. The holder whose entry triggered the refinement receives its entries afterwards, when its own factorization is built (§7.2 step 3).

If either part would be empty, nothing is moved. An implementation MUST NOT keep any record of past refinements (shared lists, forwarding links or other history structures).

### 7.5 Entering a value

A rational $m/d$ with $d \ne 0$ is entered by moving the sign of $d$ to $m$, entering $|d|$ by §7.1–7.4, and reducing $m$ against $|d|$'s support (§8.2). $d = 0$ MUST fail with the division-by-zero error.

## 8. Arithmetic

Every operation MUST read only its operands' holders, their factorizations and the base elements in their supports (S1).

### 8.1 Operands

Below, $x = m_x / p^{a}$ and $y = m_y / p^{b}$, over the current coprime base.

### 8.2 Reduction to canonical form

To reduce a numerator $m$ against an exponent vector $a$, for each $i \in \text{supp}(a)$:

1. **$p_i$ prime.** Divide $m$ by $p_i$ while it divides, at most $a_i$ times, decrementing $a_i$ each time.
2. **$p_i$ with several atoms, or an unrefined factor.** Let $g = \gcd(m, p_i)$.
   - **$g = 1$:** nothing.
   - **$g = p_i$:** divide $m$ by $p_i$ and decrement $a_i$; then, while $a_i > 0$, recompute $g$ with the remaining $m$ and apply this step again.
   - **$1 < g < p_i$:** refine $p_i$, then continue on the parts:
     - with several atoms, by the ratio-class rule of §7.3 with $f_j = \min(v_{q_j}(m),\, a_i e_j)$, the power of $q_j$ that can cancel, using copy and loop (§7.4) (M1);
     - a single unrefined factor $L$ MUST be replaced by the coprime base of $\{g, L/g\}$, computed by gcds, with every holder's factorization rewritten by copy and loop.
3. Entries whose exponent reaches 0 MUST be removed (§6.3).

The result MUST be in canonical form against the result's base elements: $\gcd(m, p^{a}) = 1$ for the final $m$ and $a$.

Reduction changes the result only, never an operand's value. After a refinement during an operation, the operation MUST continue over the refined base (M1: it restarts from its holders; long-lived local factorizations are patched by the refinement). The test for $1 < g < p_i$ MAY be made after the division loop, on the final numerator (M1); the requirement above still applies.

### 8.3 Addition and subtraction

1. Common denominator $p^{c}$ with $c = a \vee b$, read from the factorizations without a gcd.
2. $m = m_x\, p^{c - a} \pm m_y\, p^{c - b}$.
3. Reduce $m$ against $c$ (§8.2).

### 8.4 Multiplication

1. **Cross-cancel:** reduce $m_x$ against $b$ and $m_y$ against $a$, giving $m_x', b'$ and $m_y', a'$.
2. $m = m_x' m_y'$.
3. Exponent vector $a' + b'$.

For operands in canonical form, the result is in canonical form. Inside an array expression the operands MAY be unreduced, and the result is reduced by §9.4.

### 8.5 Division

$x / y$ with $y \ne 0$:

1. $\text{sgn}(m_y)$ moves to the result's numerator;
2. $|m_y|$ is entered as a denominator (§7), giving $|m_y| = p^{c}$ over the refined base;
3. the numerator is $\text{sgn}(m_y)\, m_x\, p^{b}$, with overflow checked, over $p^{a + c}$;
4. the result is reduced (§8.2).

$y = 0$ MUST fail with the division-by-zero error.

### 8.6 Comparison, negation, sign

- **Comparison** MUST compare $m_x\, p^{c - a}$ and $m_y\, p^{c - b}$ with $c = a \vee b$ as integers. At M1 bounds each fits in 128 bits; comparison MUST NOT overflow.
- **Negation** negates the numerator; it overflows only at $m = -2^{63}$ (M1 bounds).
- **Sign** and **is-zero** read the numerator.

### 8.7 Operation set (M1)

The operation set is open (§14). M1 provides:

- **Context:** create a graph; destroy a graph.
- **Values:** create from $(m, d)$; create from an integer; read as $(m, d)$ in canonical form with $d \ge 1$; clone (a new holder with the same factorization); release.
- **Arithmetic:** add, subtract, multiply, divide, negate, compare, sign, is-zero.
- **Arrays (§9):** create from fractions; create from values (copied); length; read an element as a value or as $(m, d)$; read all elements; release; elementwise add, subtract, multiply, divide; sum; dot product; begin and end an array expression.
- **Audit:** a check of I1–I4 over the whole graph (§10).
- **Also:** text conversion, `"m/d"` or `"m"` out and `"[+-]a"` or `"[+-]a/[+-]b"` in, at most 38 digits per part, a part beyond 64 bits reduced by a 128-bit gcd before entry; fused $a \cdot b + c$ on arrays; array layout and graph statistics.

## 9. Arrays

### 9.1 Common-denominator representation

An array MUST be stored as:

- a **common denominator** $D$: a holder with its own factorization;
- **dense elements** $x_j = n_j / D$: integer numerators $n_j$ with no factorization of their own;
- **exceptions**: the other elements, each a holder, in a sparse list indexed by position.

An element MUST be an exception when its denominator does not divide $D$, or when its numerator scaled to $D$ overflows. An entered denominator of $2^{63}$ is never chosen as $D$ and never dense (M1).

An array is in **canonical form as a whole** when $\gcd(D, n_1, n_2, \ldots) = 1$ over its dense elements and every exception is in canonical form. M1 enforces this by dividing $D$ and the dense numerators by their common factor, computed by a scan that stops when it reaches 1 (M1).

Elementwise operations and aggregates MUST run as integer loops over the dense elements, and through the value arithmetic of §8 only for exceptions.

### 9.2 Choosing $D$

**Provisional default:** $D$ is the lcm of the elements' denominators if it is below $2^{63}$, otherwise the most frequent denominator, the first seen on a tie (M1). At creation the rule is applied to the denominators as given; canonical form then lowers $D$ (M1).

### 9.3 Common denominator of a result

An elementwise result of arrays with common denominators $D_a = p^{\alpha}$ and $D_b = p^{\beta}$ MUST have:

| Operation | Result $D$ |
| --- | --- |
| add, subtract | $\text{lcm}(D_a, D_b) = p^{\alpha \vee \beta}$ |
| multiply | $D_a D_b = p^{\alpha + \beta}$ |
| $a \cdot b + c$ | $\text{lcm}(D_a D_b, D_c)$ (M1) |
| divide | the default rule (§9.2) applied to the results |

If that $D$ would reach $2^{63}$, every element is computed by value arithmetic and the default rule is applied to the results (M1). Aggregates produce a single value. Operands MUST have equal lengths.

### 9.4 Lazy reduction

1. Inside an array expression, intermediate results need not be in canonical form. Dense elements are taken as $n_j / D$ unreduced, and exceptions are stored unreduced (M1).
2. **Retry.** If a step overflows, its operands MUST be reduced and the step retried once. Only an overflow that survives the retry is reported.
3. **End.** At the end of the outermost expression, every array made inside it and still alive MUST be reduced once, as a whole (I4). Arrays released before the end are never reduced.
4. Expressions nest; only the outermost end reduces (M1). Outside an expression, each array operation is its own expression.
5. Value operations, element reads and aggregates MUST return canonical form, inside an expression or not. Value operations are not lazily reduced (M1).

### 9.5 Aggregates (M1)

Sum and dot product MUST be exact and independent of element order and of the dense/exception split (I5). M1 computes them as follows:

1. Accumulate in 128 bits: the dense part as one integer sum; exception terms exact in 128 bits; reduce and retry on overflow.
2. If that overflows, fall back to an order-free exact method: take every term in canonical form, sum each denominator's group exactly, and combine the nonzero groups exactly in multiprecision over their common denominator.
3. Report overflow only if the result does not fit the M1 bounds, or if that common denominator exceeds 16,384 bits.

## 10. Consistency

The factorization of a holder and the holder lists of its base elements describe the same edges from two sides. A conforming implementation MUST adopt option 1 or option 2, and MAY combine either with option 3. The choice is open (§14).

1. **Single source of truth.**
   - Edges and their exponents MUST be stored only in each holder's factorization, which is the single source of truth.
   - Holder lists MUST hold references only, with no exponents. Holder lists, reference counts, the list positions recorded in factorizations, the dictionary and any cached $p^a$ are a **derived index**, rebuildable from the factorizations and the base elements' atoms at any time.
   - An implementation MUST be able to verify the derived index against the truth, and SHOULD rebuild the index on mismatch.
2. **Shared edge records.** Each edge MUST be one record holding its exponent, referenced from both the holder's factorization and the base element's holder list.
3. **Production audits.** Audits of I1–I4, over the whole graph or in bounded increments, run periodically in production.

M1 meets option 1 except the rebuild: it stores exponents only in holders' factorizations and holder ids only in holder lists, and its audit verifies the index, but it cannot rebuild it.

## 11. Scalability requirements

- **S1. Locality.** An operation MUST touch only its operands, their factorizations and the base elements in their supports. Its cost MUST NOT depend on the size of the graph.
- **S2. Two-sided access.** Each holder's factorization and each base element's holder list MUST be available without search, so that an operation finds its base elements and a refinement finds its holders directly (§10 governs how they are stored).
- **S3. Refinement by copy and loop** (§7.4), with no record of past refinements.
- **S4. No scanning at entry.** Sharing MUST be found by dictionary lookups, never by comparing a new denominator with every base element or with every known large prime. Caches and lists consulted at entry MUST be bounded.
- **S5. Freeing.** Base elements MUST be freed by reference count, so the size of the graph is bounded by the live holders.

Costs MUST NOT grow except with the size of the numbers and, for array operations, linearly with array length.

## 12. Precision, determinism and errors

### 12.1 Precision

- **M1 bounds.** Numerators in $[-2^{63}, 2^{63} - 1]$, denominators in $[1, 2^{63} - 1]$, atoms in 64 bits, intermediates in 128 bits.
- **Overflow** MUST be detected and MUST NOT wrap. Under lazy reduction it is reported only after the retry (§9.4).
- **Exact overflow (M1).** Overflow is reported exactly when the exact result in canonical form does not fit; reducing kernels compute in 128 bits, with common denominators up to $2^{126}$, and reduce before checking. Exceptions: aggregates also report overflow when their fallback's common denominator exceeds 16,384 bits (§9.5); fused $a \cdot b + c$ checks the product first, and reports overflow if the product does not fit even when the sum would.
- **M2** extends numerators and atoms beyond 64 bits with the multi-word kernels of spec [05](../05-exact/v0.1.md); unrefined factors beyond 64 bits MUST then be refined in a way that satisfies S4.
- **Platform:** 64-bit integer arithmetic and a $64 \times 64 \to 128$-bit multiply.

### 12.2 Determinism

Every result MUST be exact. Results MUST be identical on every platform and independent of when or how the base was refined (I5).

### 12.3 Errors

1. Every fallible operation returns a status: success, overflow, division by zero, or invalid argument (M1).
2. On failure, no object is returned, and the graph MUST be unchanged except for refinements that change no value (M1).
3. **Invalid argument:** a missing object, a malformed string, an index out of range, arrays of different lengths, a buffer too small, or ending an expression that is not open (M1). A released handle gives the invalid-argument status, or a sentinel for sign, is-zero and compare (§6.6) (M1).
4. **Array division by zero** fails the whole operation, with no result (M1). An element overflow also fails the whole operation (M1).
5. **Out of memory** prints a message and aborts (M1).
6. **Limits:** arrays below $2^{32}$ elements; at most $2^{24}$ base elements and about $2^{32}$ holders per graph; exceeding them is fatal (M1).

## 13. Concurrency (future)

M1 is single-threaded: a graph and its objects MUST be used from one thread at a time; different graphs MAY be used from different threads (M1).

*The rest of this section is non-normative.* A candidate design for threads and GPUs:

- **Matrix view.** The representation is a sparse exponent matrix, rows indexed by holders and columns by base elements, plus a numerator vector.
- **Bulk operations as parallel primitives:** column-wise maximum for common denominators; per-row scaling; row hashing or sorting; batch trial division.
- **Refinement as column operations:** splitting one column into several, applied in batches.
- **Epochs.** New values and discovered refinements accumulate and are applied together at an epoch boundary. Between epochs, readers see an immutable snapshot.
- **Background refinement.** A new denominator joins as one unrefined factor, usable at once, and is factored and refined into the base by another thread. This requires a refinement method that satisfies S4.

## 14. Open decisions

- The consistency option (§10). Option 1 is recommended, provisional pending a robustness test phase with fault injection, which will decide.
- The choice of $D$ for a new array (§9.2).
- Lazy reduction for single values.
- Small-graph speed, including the per-exception cost of linking into holder lists.
- Entry cost of Pollard's rho, and the size of the bounded large-prime list.
- Refinement of unrefined factors beyond 64 bits without violating S4 (M2).
- Memory after very large refinements (storage reused only within a size class).
- The interface: printing and parsing, conversions to and from integers, floating-point numbers and spec 05's `Exact`, error reporting.
- Array errors: failing the whole operation (M1) or marking elements.
- Handling of out-of-memory without aborting.
- Concurrency (§13).
