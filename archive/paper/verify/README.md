# Checks for Appendices A and B of v0.6

These checks cover Appendices A and B of the paper: [Appendix A](../v0.6.md#appendix-a-the-library-in-nim), "The library in Nim", and [Appendix B](../v0.6.md#appendix-b-the-extension-library-in-nim), "The extension library in Nim". They are kept outside the paper. Run them from the repository root with one command:

```sh
NIM=/path/to/nim-2.2.14/bin/nim python3 paper/verify/verify.py
```

The run takes about three minutes and ends with `ALL CHECKS PASSED`, or with `FAILED` and the failing checks; the exit status is 0 or 1. `--nim PATH` names the compiler instead of `NIM` (without either, `nim` on the `PATH`; with none, the run fails). Use `--no-control` to skip the comparison with 10-interning's control, which then needs no numpy. Use `--paper FILE` to check another copy of the paper. **Nothing is timed.**

Requirements: Python 3 (tested with 3.13), `gcc` (tested with 13.3), and Nim. The control comparison also needs numpy, because 10-interning's own generator imports numpy. `control.py` finds 10-interning at the repository root or, where it now lives, under `archive/`.

**Nim** is pinned to the build that [`spec/11-matrix/nim`](../../spec/11-matrix/nim/README.md) pins: Nim **2.2.14**, from the GitHub tag `v2.2.14`, commit `c5c2337564e347bb8252a510c79a74817a670231`, built by the tag's `build_all.sh` (from `csources_v3` commit `eeab3ac46e93f10efda8e58c4db02b9438319d71`); `bin/nim` sha256 `c844c0fd004a76b1c1a6bc9b2e16a7878b375aba9dd582a29f66e667a17d0441`. The run prints whether the compiler it was given is that build, and runs with any other too. To build it:

```sh
git clone --depth 1 --branch v2.2.14 https://github.com/nim-lang/Nim nim-2.2.14
cd nim-2.2.14 && sh build_all.sh            # bin/nim
```

The checks also pass with the Nim pilot's compiler, the 2.2.13 nightly `af53f1f1545382155204d3800e9716976b588ca8` of [`spec/11-matrix/nim-pilot/REPORT.md`](../../spec/11-matrix/nim-pilot/REPORT.md).

## How it works

The paper's library is in Nim. Python stays the checking harness:

- `nimlib.py` reads the Nim code from the paper, checks it line for line against the pseudocode, compiles it, and replays on it every call the checks make.
- The checks themselves (`verify.py`, `section3.py`, `section4.py`, `control.py`) run on a **Python reference**: the harness's own mechanical translation of the same pseudocode into Python, whose integers are unbounded, checked against `fractions.Fraction`. The reference is built from the paper's pseudocode on every run, so it is not in the paper and cannot drift from it.
- Every call the checks make of a library function is recorded with the reference's result. The Nim code must then give the same result on each call whose arguments fit its 64-bit types, value for value, or an int64 overflow that an int64 model of the same pseudocode also reaches (item 10).

   - **B.2**: `import std/sequtils`, `unused`, `φ` and the type `Matrix`; `array`, `size`, `matrix`, `row_count`, `column_count`, `handles`, `values`, `cell`, `entry`, `high_word`, `home`, `probe`, `put`, `table_size`, `place`, `positions`, `copy_values`, `rewrite`, `bits`, `pack`, `place_all`, `build`, `add_cells`, `add_matrices`, `dot`, `product_cells`, `product_rows`, `multiply_matrices`.
2. **The translation is line for line** (`nimlib.check_literal`). Each function's last pseudocode definition before the appendix is its final form, read from the paper (for B.1 from chapter 3, for B.2 from sections 4.2 on). It is translated mechanically, and the appendix's function must be that text exactly, line for line and character for character. The rules are `nimlib.NIM_RULES`: `LET` to `let` (`var` for an array made by `array(n)`, which is changed in place), `IF c THEN s` to `if c: s`, `RETURN`, `SET A[i] = v` to `A[i] = v`, `DO f(x)` to `f(x)`, `·` to `*`, `−` to `-`, `/` to `div`, `=` to `==` and `≠` to `!=` in conditions, `AND` and `OR` to `and` and `or` (Nim's `and` is also the bit operation), `>>` and `<<` to `shr` and `shl`, `mod(u, v)` to `` `mod`(u, v) ``, `ERROR` to `raise newException(ValueError, …)` with the message `division by zero` (a zero divisor), `scale above 18` or `precondition`, and two spaces a level. Names are kept as the paper spells them (`b′`, `s₊`, `k₁`, `φ`). What the pseudocode does not state is fixed in the harness, not translated: each function's signature (its types), each part's head (the types and constants), and the short forms of the primitives defined in prose (`rational`, `numerator`, `denominator`; the lists, pairs and decimals of sections 3.1 and 3.4; the arrays and matrices of section 4.2; and `high_word`, below). One function works on 64-bit words, not on the library's integers: in `home`, `(v · φ) AND (2⁶⁴ − 1)` is `(uint64(v) * φ) and high(uint64)`, and `(w · n) >> 64` is `high_word(w, n)`, the top 64 of the 128 binary digits of `w · n` from 32-bit halves.
   - The Python reference is translated from the same pseudocode by `verify.translate` (`·` to `*`, `/` to `//`, `b′` to `b_prime` and so on, as before), with `pair` as a function of its own that builds a `Column`, so that its calls match the Nim code's one for one.
3. **Every function against `fractions.Fraction`.**
   - `mod` is checked on every pair with 0 ≤ u ≤ 60 and 1 ≤ v ≤ 30, and on random pairs: the result is in 0..v−1 and differs from u by a multiple of v.
   - `gcd` (the binary gcd) is checked against `math.gcd` on every pair in −30..30 except (0, 0), and on random and common-factor pairs up to 200 bits (400 bits with the common factor).
   - `reduce` is checked on every pair in −30..30 with a nonzero denominator, and on random pairs.
   - The four operations are checked on every pair of stored values with |numerator| ≤ 12 and denominator ≤ 12, which covers zero, ±1 and every sign combination. They are also checked on random values up to 200 bits, and on pairs built to hit each coincidence the special cases test for: integer operands (denominator 1), shared denominators, equal or opposite numerators, cross matches, reciprocals and common factors.
   - Every result must be a pair of integers with a positive denominator and gcd 1, and must equal the exact value.
   - Division by zero must raise `ZeroDivisionError` for every dividend tried.
   - No operation may call `reduce`, as section 2.12 says.
   - **Special cases are ordered by cost (sections 2.3 and 2.9).** For every pair with |numerator| ≤ 15 and denominator ≤ 15 (any positive denominator for sections 2.3–2.4's `add` and `multiply`, reduced values for sections 2.9–2.10's), the case reached gives a result no dearer than any other case that holds, and among cases whose results cost the same it has the cheapest test. Each special case is a top-level `if` on a, b, c and d; the order is read from the paper's pseudocode, and the harness knows only each case's cost: multiplications in the naive arithmetic; in lowest terms (gcds, multiplications, additions), compared in that order, so that x + (−x) comes before the integer cases and a cross match, which needs no multiplication, before an integer operand of `multiply`; and a test against constants cheaper than a comparison of the operands (x + (−x)'s test compares with zero when an operand is zero).
4. **Branch coverage of the Python reference.** Every `if` of the reference is traced (`sys.settrace`), both its true and its false outcome, and so is every term of each top-level `or`. Every outcome and every term must be reached, and every statement must run. The report gives the counts by the line of the paper where the pseudocode line is. (The Nim code's own coverage is item 10.) It also lists the outcomes reached only by direct calls, never from inside the four operations. These are `mod`'s outcomes (no function of Appendix A calls `mod`: the binary gcd shifts instead), `gcd`'s `v < 0` (no operation passes `gcd` a negative second argument) and `v == 0` (nor a zero one, and the binary gcd never makes one), and `reduce`'s `b < 0` and `g == 1` (no operation calls `reduce`).
5. **Section 1.3's bit examples (12 AND 10 = 8, 13 >> 1 = 6, 3 << 2 = 12), section 1.4's example, gcd(84, 36) = 12, call for call, and the worked computation of section 2.12** are reproduced exactly:
   - every call of `reduce`, `gcd`, `subtract`, `add`, `divide` and `multiply`, in order and nesting, with its arguments and result, including each step of every binary gcd chain (such as gcd(44, 30) = 2 · gcd(22, 15), … , gcd(0, 1) = 1);
   - the condition and outcome of every `if` each function evaluates, matching the paper's step tables;
   - the intermediate values (`g`, `b_prime`, `d_prime`, `t`, `h`, `p`, `q`, `k3`, …);
   - and that `reduce` and each operation run exactly once.
6. **Against 10-interning's textbook control (TC), correctness only** (`control.py`):

   - TC is built there from `10-interning/lib/src/tc.c` with round 2's own compiler commands (`r2_libconf.build_commands`, counting build only). It is run once per job in its `count` mode, the untimed mode round 2's self-tests use.

10. **The Nim code, run** (`nimlib.run`, after all of the above).
    - **Two builds.** The three parts, exactly as the paper shows them, are compiled together with a driver generated from their signatures (`nim c -d:release --mm:arc`, with overflow, range and index checks on). An instrumented copy is compiled beside it: a counter at every `if` outcome, every term of every top-level `or` and every other statement, and a call trace (each call's arguments and result, and each `if` outcome), for the calls asked for. Both builds must give the same result on every call.
    - **Every call the checks make**, of any library function, from items 3 to 9 and the control comparison (about 700 000 calls), is replayed in both builds, with its arguments as the check passed them, arrays included; for a function that changes arrays (`put`), the arrays after the call are compared too. Calls whose arguments do not fit Nim's types (an integer beyond 64 bits, such as the 200-bit random values, or the `2⁶⁴` slots of a `home` test) are not sent, and are counted by function.
    - **The int64 model.** Every call is also run on an int64 model: the Python reference's code with every integer an `int64` (each result checked against $-2^{63}$ and $2^{63} - 1$, and every `/` checked to be exact), and `home` on 64-bit words, as Nim's is. Each Nim result must equal the reference's, and then the model must give it too, or be an int64 overflow (Nim's `OverflowDefect`) that the model also reaches. ERRORs must match, message for message. A `/` with a remainder fails the check.
    - **Call trees.** The paper's examples (section 1.4's gcd(84, 36), section 2.12's worked computation, and the examples of chapters 3 and 4) and a sample of one call in 97 are traced in both languages, and each call tree must be the same: every call, in order and nesting, with its arguments and result, and the outcome of every `if` of each call, in order. So Nim reproduces section 2.12 call for call, branch for branch, as the reference does in item 5.
    - **Branch coverage of the Nim code**, by line of the paper: every `if` outcome, every `or` term and every other statement must be reached (the converters `either` and `high_word` included).


## Limits

- The Python reference's integers are unbounded; the Nim code's are `int64`, as Appendix A says. A Nim result that would not fit stops with `OverflowDefect`, and the int64 model of item 10 confirms each such overflow. About a fifth of the recorded calls have arguments beyond 64 bits and are checked in Python only.
- Two overflows of the 64-bit library are worth knowing, both found by the replay and both the pseudocode's arithmetic, not the translation's: `mod(u, v)` doubles `v` until it passes `u`, so it overflows when `u` is $2^{62}$ or more even though the remainder fits (in the library `mod` is called by `join` on a shared denominator and by `strip` on a denominator, from `to_decimal`, which can both reach it; `places` calls it on powers of 10 up to $10^{18}$, below $2^{62}$); and `gcd` cannot negate $-2^{63}$.
- The fixed-width handles of section 4.7 are not modelled, in Python or in Nim: the part `w` records the width `bits` gives, and every handle is an `int64`.
- `gcd` is recursive, as in the paper, and the binary gcd calls itself once for each binary digit it removes, so Python's default recursion limit (1000) would bound its inputs to about 1000 bits in all. `verify.py` raises the limit to 10 000; the inputs tested have at most about 800 bits in all. In Nim, `gcd` of two `int64`s makes at most 129 calls.
- Outside the paper's interface, `rational(p, 0)` is not rejected (the paper requires q ≠ 0 and does not check it), and `gcd(0, 0)` returns 0. Neither is tested.
- `tally` is recursive, as in the paper, so Python's recursion limit bounds the length of a list it tallies; the columns tested have at most a few hundred entries.
- `section4.py` raises Python's recursion limit to 20 000, since the walks over a build table call themselves once per slot (the smallest power of two from 4rc on); the largest table tested has 1024 slots, well within Nim's stack.
- The instrumented Nim build evaluates every term of an `or`, to count each term, where the paper's code stops at the first true one; the terms have no side effects, and both builds must agree on every result.
- `NIMAPPX_KEEP=DIR` keeps the Nim build, the calls and the outputs in `DIR`, for debugging the harness.
