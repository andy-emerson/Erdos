## 1. Scope

In scope: Design 1 (common divisors): its structures, operations, integer width, errors, instrumentation and correctness checks; and the boundary that says what its build contains. The control and the shared-denominator ceiling it was measured against, and the shared integer module and lookup it is built on, are specified in the joint specification ([§4.3](../partial-sharing-baseline/v0.1.md#43-width-and-integer-routines), [§5](../partial-sharing-baseline/v0.1.md#5-shared-structures-the-lists-the-lookup-and-store), [§6](../partial-sharing-baseline/v0.1.md#6-the-control), [§9](../partial-sharing-baseline/v0.1.md#9-the-shared-denominator-ceiling)); the requirements they share with Design 1 are repeated here.

Out of scope: performance targets, the workloads and the measurement rule (in the baseline's [`research/rule.md`](../partial-sharing-baseline/research/rule.md)), comparison, printing and parsing, threads, and widths other than 32 and 64 bits.

## 2. Conformance language

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are to be interpreted as described in RFC 2119 when, and only when, they appear in capitals. Sections or paragraphs marked *non-normative* state no requirement.

## 3. Terms and notation

- **Width** $w$: the number of bits of every full-width integer, 64 or 32 (§4.3).
- **Value.** A rational $m/d$ with numerator $m$ and denominator $d \ge 1$. **Lowest terms:** $\gcd(m, d) = 1$, the sign on $m$, and $d > 0$. Zero is $0/1$.
- **Class.** One set of values that share structures. A program creates a class, enters values into it, and applies operations to values of the same class.
- **Handle.** The position of a value in its class's value list: a 32-bit unsigned integer.
- **Index.** A position in a list, a 32-bit unsigned integer. Denominator index $k$ means the same denominator in every structure of a class.
- **Stored.** A value is stored when it is appended to its class. A stored value is never changed. Every result is stored as a new value.
- **Entry.** Storing a value given from outside as an integer pair $(m, d)$. **Operation:** add, subtract, multiply or divide, on two stored values, storing the result.
- **Residual** of $d$ at a divisor $c$: $d / c$.
- **Gcd-first method:** reduced-rational arithmetic that takes the gcd of the two denominators before forming the sum, and takes cross gcds before forming a product (§6).
- $\text{bits}(x)$ is the number of bits of $|x|$; $\text{bits}(0) = 0$.
- **Island:** in Design 1, a denominator in no compared pair. Every new denominator starts as an island, with one entry in its sparse incidence row: (divisor 1, its own value) (§7.4).

## 4. Requirements on every implementation

### 4.1 Interface

Design 1 MUST provide, as the control and Design 2 do (joint §4.1):

| Call | Effect |
| --- | --- |
| `create()` | a new, empty class |
| `destroy(class)` | frees the class and everything in it |
| `enter(class, m, d)` | stores $m/d$ in lowest terms; returns its handle, or an error |
| `add`, `sub`, `mul`, `div` `(class, x, y)` | stores the result of $x \circ y$; returns its handle, or an error |
| `read(class, x)` | returns the numerator and denominator of $x$, in lowest terms |
| `size(class)` | the number of stored values |
| `memory(class, report)` | fills the memory report of §12.2 |
| `counters(class, report)` | fills the counters of §12.1 (counting build) |
| `audit(class)` | the **full audit**: checks every invariant of §13.2; returns pass or the first failure (test build) |
| `audit_changed(class)` | the **incremental audit** of §13.2: checks only what changed since the last audit; returns pass or the first failure (test build) |
| `audit_scheduled(class)` | the full audit as §13.3 item 2 schedules it before the last call; in Design 1, the same as `audit` (§13.3's large-base rule applies to Design 2 only) (test build) |

*Amendment, Oct 28, 2026:* `audit_scheduled` is added (library DEC-2). §13.3's large-base rule changes every scheduled full audit except the last, which `audit(class)` cannot tell apart; `audit` stays the complete audit and is the one run after the last call.

### 4.2 Values

1. Every stored value MUST be in lowest terms, with the sign on the numerator and a positive denominator.
2. Zero MUST be stored as $0/1$, whatever operation produced it.
3. Subtraction MUST be computed as addition of the negated second operand: $x - y = x + (-y)$. Negation changes no denominator.
4. `enter` MUST move the sign of $d$ to $m$ and reduce $m/d$ by $\gcd(m, d)$ before storing.
5. A stored value MUST NOT be modified, moved to another handle, or freed before its class is destroyed.

### 4.3 Width and integer routines

1. Every full-width integer (numerators, denominators, divisors, residuals, intermediates) MUST have one width $w$, chosen by a single build setting. The default MUST be 64; 32 MUST be supported by a rebuild with no change to source.
2. Numerators MUST lie in $[-(2^{w-1} - 1),\ 2^{w-1} - 1]$ and denominators in $[1,\ 2^{w-1} - 1]$. The most negative integer is excluded, so negation and absolute value never overflow.
3. An implementation MUST NOT use an integer wider than $w$ for any full-width intermediate. The lookup hash and index arithmetic (positions in lists and rows, and the pair set's keys) are not full-width arithmetic: the hash MUST use unsigned 64-bit wrapping arithmetic at every width, including $w = 32$ (§5), and positions MUST use unsigned integers of at least 32 bits.
4. All implementations MUST use one shared module of integer routines, and no other full-width arithmetic:
   - **gcd**: the binary method (removing common factors of 2 by counting trailing zeros, then subtracting), on magnitudes, with $\gcd(a, 0) = |a|$;
   - **checked add, subtract and multiply**, each reporting overflow (§4.4);
   - **exact division** of $a$ by a known divisor $b$ (the hardware divide);
   - **division with remainder** (the hardware divide), used for divisibility tests;
   - **bit routines**: popcount, highest set bit and trailing zeros of a 64-bit word, and $\text{bits}(x)$.
5. In the counting build (§12.1), every routine of item 4 MUST count its calls, by the counting rules of §12.1.

### 4.4 Overflow

1. Every full-width addition, subtraction and multiplication MUST be checked. A result outside the ranges of §4.3 item 2 MUST be reported as overflow. Overflow MUST NOT wrap silently.
2. On overflow the operation MUST return the overflow error, store no value, and record where it happened: the operation, the handles of its operands, and the step (named as in the pseudocode).
3. The class MUST remain valid after an overflow: every invariant of §13.2 holds. Changes made before the overflow that change no stored value (Design 1's recorded gcds) MAY remain.
4. The harness excludes a trial that reports any overflow from the comparisons. The measurement rule's workloads make overflow impossible, so it treats such an overflow as a bug (the rule says how).

### 4.5 Errors

1. `enter` with $d = 0$, and `div` with $y = 0$, MUST return the division-by-zero error and store nothing.
2. A handle not in the class MUST return the invalid-argument error.
3. Out of memory MUST print a message and abort.
4. Exceeding the limits of §14 MUST abort with a message.

### 4.6 Language and build

1. Each implementation MUST be written in C (C11), single-threaded, with no library beyond the C standard library.
2. All implementations MUST be compiled by the same compiler with the same flags.
3. There MUST be three builds of the same source, differing only in compile-time settings:
   - the **timing build**: counters and audits compiled out;
   - the **counting build**: counters compiled in, audits out;
   - the **test build**: counters and audits compiled in.
4. Counters and audits MUST NOT change the control flow or the results of any operation.

## 5. Shared structures: the lists, the lookup and `store`

Design 1 MUST keep the following three structures, as Design 2 does. The control keeps only a value list (joint §6), and the ceiling its vectors (joint §9).

| Structure | Shape | Each entry stores |
| --- | --- | --- |
| Numerators | list of $N$ | the numerator ($w$ bits) and its denominator index (32 bits) |
| Denominators | list of $D$ | the denominator ($w$ bits) |
| Lookup | array of $S$ slots | a denominator index, or empty |

1. **Lists.** A list MUST only grow at its end. An index, once given, MUST refer to the same entry for the life of the class. A handle is a position in the numerator list.
2. **Lookup.** The lookup MUST be a hash table of denominator indices with linear probing:
   - $S$ is a power of two, initially 16;
   - before an insertion would make the table more than half full, $S$ MUST double and every index MUST be placed again, in index order;
   - the starting slot of a value $v$ is $\lfloor (v \cdot \phi \bmod 2^{64}) / 2^{64 - \log_2 S} \rfloor$ with $\phi = \text{9E3779B97F4A7C15}_{16}$, computed with unsigned 64-bit wrapping arithmetic at every width, including $w = 32$ (this is index arithmetic, not a full-width operation, is allowed by §4.3 item 3, and is not overflow-checked);
   - a probe reads the index in a slot and compares the denominator list's value at that index; a slot holds an index, never a value; the search moves to the next slot, wrapping at the end, until it finds the value or an empty slot.
3. **Fast path.** When two operands have equal denominator indices, an operation MUST take the same-denominator path given in its pseudocode.

The procedure `store(n over e)` appends a result:

```text
function store(n over e)
    if n is 0 then
        set e to 1
    end if
    look e up
    if e is found at index k then
        append (n, k) to the numerators
    else
        append e to the denominators as index k
        place k in the lookup
        create the structures of the new denominator k        §7.4
        append (n, k) to the numerators
    end if
    return the handle of the new numerator
end function
```

In Design 1 the operation passes only $n$ and $e$ (§7.4).

## 7. Design 1: common divisors

Design 1 MUST be built in the note's **implementation form**: six structures, as follows.

*Amendment, Oct 29, 2026, approved by the author: the pair set.* The dense pair table, the upper triangle of $D \times D$ at 1 bit per cell, is replaced by a hash set of the pairs that have been compared. Its meaning is unchanged: a pair is inserted exactly when the table would have set its bit, and "is the pair compared" becomes "is $(i, j)$ in the set". Its memory is proportional to the number of compared pairs, not to $D^2$.

*Amendment, Oct 29, 2026, approved by the author: sparse incidence rows.* The dense incidence matrix, $D$ rows of $\lceil C/64 \rceil$ words, and the residual rows are merged into one **sparse row** per denominator. A row lists only the facts that exist: one entry (divisor id, residual) for each divisor known to divide $d_k$, sorted by divisor value. Divisor ids are stable: a new divisor takes the next id, so no row is shifted or renumbered when a divisor is inserted. The search merges two rows from the largest divisor down and stops at the first divisor common to both. The facts, the results, the pair set's behaviour and the counters' meanings are unchanged; a row-merge step counts as a scan (§12.1). This replaces the former items "Incidence bits" and "Residual rows", §7.2's word-by-word search, and the shifting of §7.3.

### 7.1 Structures

| Structure | Shape | Each entry stores |
| --- | --- | --- |
| Numerators, denominators, lookup | §5 | §5 |
| Divisors | list of $C$ by **id**, in order of insertion; id 0 is $1$; with the list of ids sorted by value | a common divisor found so far ($w$ bits), and its id in the sorted list (32 bits) |
| Pair set | a hash table of $S_P$ slots, 64 bits each | a compared pair $(i, j)$, $i < j$, or empty |
| Incidence rows | one sparse row per denominator, of varying length, sorted by divisor value | (divisor id, residual $d_k / c$) for each divisor $c$ known to divide $d_k$ (32 + $w$ bits) |

1. **Pair set.** The pair $(i, j)$, $i < j$, is the 64-bit key $j \cdot 2^{32} + i$; no key is 0, so 0 marks an empty slot. The set MUST be a hash table with linear probing, using the lookup's hash (§5 item 2) on the key.
   - $S_P$ is a power of two. It is 0 until the first insertion, then 16.
   - Before an insertion would make the table more than half full, $S_P$ MUST double, and every key MUST be placed again, in the order of the old slots.
   - A membership test hashes the key and probes until it finds the key or an empty slot.
   - There is no key for $i = j$, and a new denominator adds nothing to the set.
2. **Divisors.** A divisor's id MUST never change. A new divisor MUST take id $C$, and its id MUST be inserted into the sorted list at its value's place; nothing else moves.
3. **Incidence rows.** Divisor 1 is explicit: entry 0 of every row MUST be (id 0, $d_k$). A row's entries MUST be strictly increasing by divisor value. Only actual facts "$c$ divides $d_k$" are stored.
4. An entry and a pair in the set MUST never be removed or changed, except that entries move up within their row when one is inserted before them.

### 7.2 The search

```text
function search(i, j)
    set a to the last entry of row i and b to the last entry of row j
    loop                                                   one scan per step
        if the ids of a and b are equal then
            return (a, b)
        end if
        if the divisor of a is larger than that of b then
            move a down by one entry
        else
            move b down by one entry
        end if
    end loop
end function
```

The returned entries hold the largest divisor known to divide both $d_i$ and $d_j$, and the residuals of both at it. Divisor 1, entry 0 of every row, always qualifies, so the merge always stops. `residual(k, ·)` is the residual of the entry found; no other read is needed.

### 7.3 Compare and record

`compare(i, j)` returns the id of $\gcd(d_i, d_j)$ and the residuals of $d_i$ and $d_j$ at it, recording the gcd if the pair has not been compared.

```text
function compare(i, j)
    set (a, b) to search(i, j)
    set id to the id of a, r_i to the residual of a and r_j to the residual of b
    if (i, j) is in the pair set then
        return (id, r_i, r_j)                            the gcd, by §7.6
    end if
    set c to divisor[id]
    set g' to gcd(r_i, r_j)
    if g' is 1 then
        insert (i, j) into the pair set
        return (id, r_i, r_j)                            g is c
    end if
    set g to c · g'
    find g in the ids sorted by value, by binary search
    if g is present then
        set id_g to its id
    else
        set id_g to C, append g to the divisors as id C
        insert id_g into the sorted ids at g's place
    end if
    set s_i to r_i / g' and s_j to r_j / g'              the residuals at g
    for each row k in i, j, with its entry e_k from the search, do
        find g's place among the entries of row k above e_k, by binary search      one scan per entry read
        if row k does not hold id_g there then
            insert (id_g, s_k) at that place
        end if
    end for
    insert (i, j) into the pair set
    return (id_g, s_i, s_j)
end function
```

Inserting a divisor MUST NOT shift or renumber any row: only the sorted list of ids moves, and only the two rows that gain $g$ get an entry. Since $g > c$, its place in row $k$ is above the entry where the search stopped.

### 7.4 New denominators: islands

When `store` adds a new denominator $k$ with value $e$, it MUST:
- append an incidence row with one entry, (id 0, $e$): divisor 1, with residual $e$;
- add nothing to the pair set.

This holds for every source: entry, a zero result (§5), and every operation, whatever it knows about $e$. A new row MUST NOT hold any divisor but 1, and building it computes no gcd, division or multiplication. In particular, a new row MUST NOT copy an operand's row, even where the operation knows $e = d_k \cdot \mu$ with $\mu$ in hand (§15.2).

A pair MUST be inserted only by `compare`, and `compare` MUST be called only by addition, subtraction and division on two operand denominators with $i \ne j$. Multiplication MUST NOT insert a pair. So a new denominator is an island: it is in no pair, and no divisor but 1, until it is compared as an operand.

*Example* (non-normative), continuing the note's example: after $\tfrac{1}{12} + \tfrac{5}{18}$, the new denominator $36$ is $\{1{:}36\}$, though $6$ divides it; row $36$ gains a divisor other than 1 only when $36$ is compared, as an operand, with a denominator it shares a factor with.

### 7.5 Operations

```text
function add(m_x over d_i, m_y over d_j)
    if i is j then
        set t to m_x + m_y
        set h to gcd(t, d_i)
        return store((t / h) over (d_i / h))
    end if
    set (id, r_x, r_y) to compare(i, j)
    set g to divisor[id]
    set t to m_x · r_y + m_y · r_x
    if g is 1 then
        set h to 1
    else
        set h to gcd(t, g)
    end if
    return store((t / h) over (r_x · (d_j / h)))
end function

function multiply(m_x over d_i, m_y over d_j)
    if i is j then
        return store((m_x · m_y) over (d_i · d_i))
    end if
    set (a, b) to search(i, j)                            no compare, no pair inserted
    set r_x to the residual of a and r_y to that of b
    set g_1 to gcd(m_x, r_y)
    set g_2 to gcd(m_y, r_x)
    return store(((m_x / g_1) · (m_y / g_2)) over ((d_i / g_2) · (d_j / g_1)))
end function

function divide(m_x over d_i, m_y over d_j)
    if m_y is 0 then
        fail with division by zero
    end if
    set s to the sign of m_y and t to |m_y|
    set g_1 to gcd(m_x, t)
    if i is j then
        return store((s · (m_x / g_1)) over (t / g_1))
    end if
    set (id, r_x, r_y) to compare(i, j)                  r_x = d_i / gcd(d_i, d_j), r_y = d_j / gcd(d_i, d_j)
    return store((s · (m_x / g_1) · r_y) over (r_x · (t / g_1)))
end function
```

### 7.6 Why the search is exact (non-normative)

If $(i, j)$ is in the pair set, $\gcd(d_i, d_j)$ was recorded in both rows when the pair was compared, and no pair or row entry is ever removed; no common divisor exceeds the gcd; so the divisor the search finds is the gcd. If the pair is not in the set, the divisor found is a common divisor $c$, and $\gcd(d_i, d_j) = c \cdot \gcd(d_i/c,\ d_j/c)$. The merge finds the same divisor as an AND of dense rows would: the largest value present in both rows. A new row holds only divisor 1 (§7.4), which is true of every denominator.

## 10. The skeleton's boundary

Each build MUST be an accurate representation of the skeleton: the plainest correct form of the design. Bugs and plain inefficiencies inside the skeleton are fixed. Nothing outside it is added.

**Inside the skeleton:**
- one fixed integer width, 64 bits, set in one place, with overflow detected; schoolbook arithmetic;
- the same gcd and division routines as in Design 2, the control and the ceiling;
- the denominator lookup: a hash table of indices, with linear probing, growing when half full;
- Design 1's pair set, holding only the compared pairs (§7.1); sparse incidence rows of (divisor id, residual), sorted by divisor value, searched by a merge from the top (§7.1, §7.2);
- stable divisor ids, with sorted insertion into the list of ids by value (Design 1);
- **no result reuse in Design 1:** a new result denominator enters with divisor 1 only (§7.4) (result reuse is kept in Design 2 only, under the ruling R-1, §15);
- **no work in advance, no work in the background; each operation computes only what it needs** (as in Design 2).

**Outside the skeleton** (possible later improvements, MUST NOT be built):
- threading, GPUs, SIMD intrinsics and batching in phases;
- background (eager) comparisons;
- linking a new divisor to every other denominator it divides (Design 1);
- recording about a result's denominator more than §7.4 gives: copying an operand's row into it, divisibility tests of known divisors, new divisors formed from the operation's quantities, or facts added to an existing denominator's row;
- the **lazy parent link** (Design 1, deferred): a result row records a parent $k$ and a factor $\mu$ with $e = d_k \cdot \mu$, and the search consults the parent's row on demand;
- the index-valued pair table (Design 1);
- deferred re-sorting of divisors (Design 1);
- cluster maintenance;
- integers wider than $w$, p-adic methods, BLAS, fast multiplication.

## 12. Instrumentation

### 12.1 Counts

In the counting build, the implementation MUST count, separately for each **phase** (entry, add, subtract, multiply, divide) and, within an operation, separately for its **core** (everything before `store`) and its **store** (lookup, append and the new denominator's structures):

| Counter | Counts |
| --- | --- |
| gcds | calls of the shared gcd, with a histogram of $\text{bits}$ of the larger operand (bins 0 to 64) and the sum of those bits (the **gcd work**) |
| divisions | exact divisions and divisions with remainder |
| multiplications | full-width multiplications |
| additions | full-width additions and subtractions |
| lookups | lookup searches, slot probes, and pair reads (one per membership test of the pair set) |
| scans | row-merge steps in searches, and row entries read in the binary search for $g$'s place in a row (§7.3), counted whether or not the row already holds $g$ |
| refinements | divisors inserted |
| events | compares (pair not in the set) and pair hits; same-index fast paths, new denominators, overflows |

**Counting rules.** The implementation MUST count the following cases in exactly this way, as every row of the joint build does:
1. **The sign.** Multiplying by the sign $s$ of $m_y$ in division is not counted.
2. **Repeated division.** "Divide rest by $q$ as many times as it goes" counts one division with remainder per attempt, including the final attempt that fails.
3. **The gcd.** A gcd counts as one gcd, entered in the histogram with its operand sizes. The subtractions, shifts and trailing-zero counts inside it are not counted as additions, divisions or bit routines.
4. **Index arithmetic and hashing.** Arithmetic on positions and on the pair key $j \cdot 2^{32} + i$, and the hashes of the lookup and the pair set are not counted as additions or multiplications. They are counted as lookups: one lookup search per hash computed, one probe per slot read (in the lookup and in the pair set, insertions and re-placements on growth included), and one pair read per membership test of the pair set.

*Amendment, Oct 28, 2026:* §4.3 item 5 requires every routine to count its calls, but the table above has no row for the bit routines. Their calls are counted in a further counter, **`bitops`** (library DEC-8; the trailing-zero counts inside the gcd are excluded by rule 3, and so is the instrumentation's own $\text{bits}$ for the histogram). `bitops` is **reported only**, with every other counter of this section (rule item 6); it enters no measure: not the gcd work, nor any verdict, band or flag.

*Amendment, Oct 29, 2026 (approved by the author, with §7):* the Design 1 entries above now say "pair" where they said "pair bit", with the same meaning. The library names its counters in its DECISIONS.md.

*Amendment, Oct 29, 2026 (approved by the author, with §7's sparse rows):* Design 1's scans now count steps of the row merge, one per pair of entries compared, the final match included (where one word ANDed counted one), and entries read in the binary search for $g$'s place in each of the two rows (where one word popcounted counted one), counted whether or not the row already holds $g$, as in §7.3's pseudocode. Words shifted and stride growths no longer occur. Each counter keeps its meaning as the cost of the same step.

The counters MUST be readable at any time, and MUST be reset only by `create`.

### 12.2 Memory

`memory` MUST report, for every structure, the **used bytes** (entries times entry size, plus every per-row header) and the **allocated bytes** (capacity). The structures and their entry sizes at $w = 64$:

| Implementation | Structure | Used bytes |
| --- | --- | --- |
| Design 1 | numerators | $12N$ |
| Design 1 | denominators | $8D$ |
| Design 1 | lookup | $4S$ |
| Design 1 | divisors | $12C$ (the values, and the ids sorted by value) |
| Design 1 | pair set | $8 S_P$ (the whole table, as for the lookup; $S_P \le 4 \times$ the compared pairs, or 16) |
| Design 1 | incidence rows | $12 \times$ (row entries) + headers |

A per-row header MUST be counted at its real size and SHOULD be at most 16 bytes. **Bytes per rational** is the total used bytes divided by the number of stored values $N$. Allocated bytes per rational is reported beside it.

### 12.3 Timing

The harness times phases; the implementations hold no timers. The harness MUST time entry, operations and read-out separately, with a monotonic clock read only between calls, never inside one.

## 13. Correctness

### 13.1 Against an exact reference

Every stored value of every run MUST be read out and compared with an exact reference computed with arbitrary-precision rationals, independently of the shared integer routines: numerator and positive denominator, both in lowest terms, must be equal. Any mismatch fails the run for that implementation.

### 13.2 Invariants

`audit` MUST check, in the test build:

- **All:** every stored value is in lowest terms with a positive denominator; zero is $0/1$.
- **Denominators:** every denominator index is found by the lookup at its value; the lookup holds exactly $D$ indices and is at most half full; the denominator list has no duplicates.
- **Design 1:**
  - divisor id 0 is 1; the sorted list holds every id once, in strictly increasing order of value;
  - entry 0 of every row is (id 0, $d_k$); every id in a row is below $C$; each row is strictly increasing by divisor value;
  - for every entry (id, residual) of row $k$: $\text{divisor}[\text{id}] \cdot \text{residual} = d_k$;
  - the pair set's size is a power of two (or 0), it is at most half full, its count equals the keys it holds, and every key is a pair $i < j < D$ found at its slot;
  - for every pair $(i, j)$ in the set: the divisor at `search(i, j)` equals $\gcd(d_i, d_j)$.

`audit_changed` MUST make the same checks, restricted to what changed since the last audit (full or incremental):
- **All:** the values stored since then.
- **Denominators:** the denominators added since then, each found by the lookup at its value; the lookup's count and load.
- **Design 1:** each divisor inserted since then, against its two neighbours; the rows created since then (divisor 1 only), and the rows that gained an entry, each in full; the pairs inserted since then, each found in the set; the set's load.

The test build records what changed in a change list that only the audits read; recording it MUST NOT change any result (§4.6 item 4).

### 13.3 Tests

1. Unit tests MUST cover: every worked example of the design note, with the stated intermediate structures; zero operands and zero results in every operation; negative numerators; division by zero; equal-index fast paths; a denominator of 1; an overflow in each operation; the pair set (empty until a pair is compared, growth at half full, either order of a pair, no insertion by multiplication, a membership test counted as a lookup), and a new result denominator of each operation, including one known to be a multiple of an operand's denominator, checked to hold divisor 1 only, with residual $e$, and a result found by the lookup, whose existing row is unchanged; and the example of §7.4.
2. **The gate.** Every job of the measurement rule MUST pass, in the test build and before any measured run, one complete run (entry, operations and read-out) audited on this schedule. Every call that stores a value counts: `enter` and the operations, so **entries are audited**, on the same schedule as operations.
   - a full audit (`audit`) after each of the first 200 calls of the job;
   - then a full audit after every 64th call (calls 256, 320, 384, …);
   - a full audit after the last call.

   Between full audits, the test build MAY run `audit_changed` after every call.

3. The 32-bit build MUST pass the unit tests.

*Non-normative: the gate's cost.* A job of $n_c$ calls gets about $200 + n_c / 64$ full audits: about 670 for the rule's 30,000-call jobs. Every full audit of Design 1 is linear in its structures (values, lookup, rows and pair set), a few milliseconds each, a few seconds per job.

## 14. Limits

Fewer than $2^{32} - 1$ stored values, denominators and divisors per class; exceeding them aborts (§4.5).

## 15. Choices not settled by the design note

Each item is a choice this specification makes where the note is silent or leaves room; each is local to the sections named. All are approved by the author, Oct 28, 2026, and are fixed before any measurement.

- **G-1** (§4.2, §5, §6). A zero result is stored as $0/1$ by `store`, as the note now states for addition.
- **G-2** (§4.3). Numerators exclude $-2^{w-1}$; denominators are signed and at most $2^{w-1} - 1$.
- **G-3** (§4.3). No full-width intermediate wider than $w$; overflow of any intermediate is overflow, even when the reduced result would fit. The lookup hash is index arithmetic and uses unsigned 64-bit arithmetic at both widths.
- **G-4** (§4.3). The shared gcd is the binary method.
- **G-5** (§5). The lookup's hash multiplies the value by a fixed odd 64-bit constant (about $2^{64}$ divided by the golden ratio) and keeps the top $\log_2 S$ bits, rather than taking the value mod $S$, which clusters on denominators with many factors of 2; initial $S = 16$.
- **G-6** (§4.6). Three builds of one source; timing runs carry no counters.
- **D1-1** (§7.1). *Superseded Oct 29, 2026 by D1-5:* incidence rows were one contiguous array, growing one word of stride at a time.
- **D1-2** (§7.3). A recorded residual is computed as the residual at $c$ divided by $g'$, as the note says.
- **D1-3** (§7.4, §7.5). A new result denominator enters as in the original skeleton: divisor 1 only, residual $e$, in no pair. It does not copy an operand's row, even where the operation knows $e = d_k \cdot \mu$ with $\mu$ in hand. Required under R-1 (§15.2).
- **R-1** (§7.4, §8.3, §10). **The author's ruling, Oct 28, 2026 (option 2).** Each design uses only the result reuse that its own structure gives for free: reuse is allowed only where it is **what the design's own production implementation would naturally do**. Design 2's reuse qualifies, because the valuations of a result's denominator are a direct output of its arithmetic, and only the unknown part is refined (D2-3). Design 1's eager copy of an operand's row into the result's row, residuals times $\mu$, does not, because a production version would more likely be lazy; it is removed (D1-3). The lazy and deferred forms are later improvements, outside the baseline (§10, §15.2).
- **M-1** (§12.2). Bytes per rational uses used bytes, with allocated bytes reported beside it; per-row headers are counted.
- **I-1** (§12.1). Counts are split into entry and the four operations, and within an operation into core and store, so a result's entry cost is visible inside the operation.
- **I-2** (§12.1). The counting rules: the sign is not counted; repeated division counts every attempt, the failing one included; a gcd counts once, its inner steps not at all; index arithmetic and the hash count as lookups, never as arithmetic.
- **T-1** (§4.1, §13.2, §13.3). The gate audits in full after each of the first 200 calls, then after every 64th call and after the last; entries count as calls. Between full audits an incremental audit MAY run after every call.
- **D1-4** (§7.1). *Oct 29, 2026, approved by the author.* The pair set is a hash table of 64-bit keys $j \cdot 2^{32} + i$, with the lookup's hash and linear probing, empty until the first insertion, then 16 slots, doubling before it would pass half full. Its memory is the whole table, $8 S_P$, as the lookup's is $4S$.
- **D1-5** (§7.1–§7.3). *Oct 29, 2026, approved by the author.* Incidence rows are sparse: entries (divisor id, residual), sorted by divisor value, with divisor 1 explicit as entry 0. Divisor ids are append-only, and a list of ids sorted by value serves the binary search for $g$. The search is a merge of two rows from the top, and a new residual's place is found by a binary search of the row above the merge's stop. One scan per merge step, and one per entry read.
- **B-1** (§10). The "outside" list of §10 adds to the note's list, so that builders cannot read these as allowed: SIMD intrinsics; the index-valued pair table, deferred to a later test; and integers wider than $w$. (Its items for Design 2 and the control are in the joint text.)

### 15.1 Plain inefficiencies removed

At the author's direction, the following repeated work, found in the procedures of the design note or of the earlier draft of this text, is removed. None changes a stored value, a structure or what is recorded; each removes only computation whose result was already known within the same call, could not change, or was not used. The note is in line with every item.

- **D1-a** (§7.3, §7.5). `compare` returns the residuals at the gcd, which it already knows ($r_k / g'$, or the residuals it read), so addition and division do not read them again (formerly by popcount).
- **D1-b** (§7.3). When $g' = 1$, `compare` inserts the pair and returns at once, with no binary search and no row test: $g$ is $c$, already recorded in both rows.
- **D1-c** (§7.3). A divisor inserted at the end of the list (above every divisor) shifts no row, since no row has a bit at or above the old $C$. *Since Oct 29, 2026 (D1-5), no insertion shifts a row.*

### 15.2 Result reuse

Under the author's ruling R-1 (Oct 28, 2026, option 2), each design uses only the reuse that its own structure gives for free, the way a production implementation of that design would naturally do it, at a new denominator only, with no gcd. The note is in line with this item; Design 2's (D2-c, kept) is in [its specification](../09-coprime-base/v0.1.md#152-result-reuse).

- **D1-d** (§7.4). **Removed.** The eager copy of an operand's row into a new result's row, each residual times $\mu$ (where $e = d_k \cdot \mu$), is not built. It does not qualify: its facts are not an output of the operation's arithmetic but a copy of another row, and a production version would more likely be lazy (below). Design 1's new rows hold one entry only, (divisor 1, $e$), as in the original skeleton.

**Deferred** (later improvements, outside the baseline, §10):
- **Design 1's lazy parent link.** A result row records a parent $k$ and a factor $\mu$ with $e = d_k \cdot \mu$; the search consults the parent's row on demand, instead of copying it.

**Left out** (outside the skeleton, §10): tests of known divisors against a result's denominator, new divisors formed from the operation's quantities (each would be an insertion into the divisors and a row), and facts added to a denominator the lookup finds.
