# Signed Integers with a Header: Specification v0.1

Nov 1, 2026 · Records the author's decisions of Nov 1, 2026. Details that follow from them are marked **(coordinator's call)**. Integers on the CPU only. Checked against [`../../RULES.md`](../../RULES.md) by the coordinator. Nothing is built or run.

## 1. The representation

Every number is an **8-bit header** and a **64-bit word**, 72 bits. Headers and words are kept in two parallel lists (header $i$ belongs to word $i$), so a header is never padded to 8 bytes.

- **Header:** bits 0–4 the class code $c$; bit 5 spare, always 0; bits 6–7 the direction $d$, a counter mod 4 for $1, i, -1, -i$ (paper v0.7, §2.3). **(Coordinator's call:** the direction sits at the top of the byte, so a byte add of two direction fields wraps mod 4 with the carry falling off.**)**
- **Word:** always an unsigned magnitude or a slot index, never signed.
  - $c = 0$: the word is the magnitude, up to 64 bits.
  - $c = 1, \dots, 31$: the word is a **slot index** (not a pointer) into the pool for width $2^{c+6}$ bits (128 to $2^{37}$ bits). Every slot in a pool has exactly that width, words lowest first.
- **Canonical form:** each number is stored in the smallest class that holds its magnitude, and zero is header 0, word 0 (one zero, on no axis).
- **Word size $W$** is a parameter. Only $W = 64$ is timed. The layout is little-endian, so a list of 64-bit words is byte-identical to a list of 32-bit words twice as long. The check also runs $W = 32$, as spec 12 did for Growing. **(Coordinator's call.)** A GPU form is out of scope: there is no GPU to test on.
- **Directions:** integer operations produce only $d = 0$ and $d = 2$. $i$ and $-i$ are representable, but complex values (sums across axes, which need expressions with at most one term per axis) are out of scope for a later spec. An add across axes is reported as an error.

Directions follow §3. Opposite directions use Growing's `opAbsdiff2` (subtract, then negate on the final borrow). **(Coordinator's call:** Control gets the same header list and direction arithmetic, so that the one idea measured is the class code.**)**
2. **Header** (general improvement). The representation of §1: an inline word for class 0, fixed-width pools above it.

**(Coordinator's call:** no separate build for the inline word alone. It was measured as Hybrid in spec 12's round 5, and job 1 here touches no pool, so job 1 measures it and the larger jobs measure the pools.**)**

## 3. Operations

Six operations run on **every build and every job, with no exceptions**: add, subtract, multiply, exact division, gcd and compare. Add runs twice on the same magnitudes: with random directions, and with both directions 1. **(Coordinator's call:** the difference is the cost of the opposite-direction branch.**)**

**Direction arithmetic** (mod 4, on the header only):
- multiply: $d_1 + d_2$; exact division: $d_1 - d_2$; negate: $d + 2$;
- add, equal directions: magnitude $m_1 + m_2$, direction $d_1$;
- add, opposite directions: magnitude $\lvert m_1 - m_2 \rvert$ and its borrow $b$ (1 when $m_1 < m_2$), direction $d_1 + 2b$;
- subtract: negate the second, then add;
- gcd: direction 0; compare: by direction, then by magnitude (class code first, which decides when the classes differ, since the form is canonical), returning $-1$, 0 or 1;
- any zero result gets header 0.

**Result class** (Header). Let $L = \max(c_1, c_2)$. The class is predicted from the headers: add with equal directions $L + 1$; add with opposite directions $L$; multiply $L + 1$; exact division $c_1$; gcd $\min(c_1, c_2)$, or the other operand's class when one is zero. The routine allocates a slot of the predicted class, computes into it, finds the top nonzero word, and if the result fits a smaller class, moves it there and releases the slot. When the predicted class is 1 and both operands are class 0, the two-word result is held in registers and a slot is taken only if the high word is nonzero. **(Coordinator's call.)** A result past class 31 is reported as an error.

**Mixed classes.** The smaller operand is first widened to the larger class: copied, zero-extended, into a local buffer. Add, subtract, multiply and compare then run at the full class width ($n$ words in, $n$ or $2n$ out). Exact division and gcd run Growing's routines on the widened words, writing into the slot. **(Coordinator's call:** they shrink their working lengths as Growing does; this shares one routine per operation across both builds.**)**

**Pools** (Header). One table entry per class: base pointer, capacity, next unused slot, free-list head.
- **Release:** values are immutable, and the owner releases a number explicitly, as with Growing's `release`. Releasing a class-0 number does nothing; releasing a slot pushes its index onto the pool's free list, kept in the freed slot's first word, so the free list needs no structure of its own.
- **Allocation:** pop the free list, else take the next unused slot, else grow.
- **Growth:** when full, the pool doubles its capacity, starting at 16 slots, by reallocating and copying. Indices stay valid; pointers into the pool do not, so an operation allocates its result slot before it computes its operands' addresses. Pools never shrink. **(Coordinator's call.)**

**Structures** (rule 4). Stored: the slot, for classes above 0. Temporary: the predicted slot, when the result moves down. Local: the widened operand, or Growing's one buffer in division and gcd, which holds the widened copy. The pools take the place of `malloc`.

**Special cases** are not built. Named for later: (a) skipping the widening by reading absent words as zero; (b) same-direction add allocating class $L$ and moving up only on a carry; (c) multiply by a class-0 operand as a one-word loop.

## 4. Operands

All from one seeded Python generator, the same for both builds; 1024 operations per operation and job, as in spec 12.
- **Directions:** 1 or $-1$ with probability 1/2 each.
- **Size jobs:** job 1 has bit lengths 1 to 64. For $k \in \{2, 4, 8, 16\}$ words there are two jobs: **$k$-full**, lengths $64k - 31$ to $64k$ (little rounding), and **$k$-half**, lengths $32k + 1$ to $32k + 32$ (just over half the class, most rounding). **(Coordinator's call.)**
- **Mixed job** (the common case): each operand is one word with probability 15/16, else drawn from a size job chosen uniformly. **(Coordinator's call:** a placeholder rate; the author should set it.**)**
- **Growth job:** 64 chains, each from a random one-word value $x$, of 32 steps $x \leftarrow x \cdot y + z$, with $y$ and $z$ random signed one-word values ($y \ne 0$). Each intermediate is released inside the clock. $x$ grows to about 33 words, so pools 1 to 6 fill, empty and reuse slots. Reported as time per step. **(Coordinator's call.)**
- **Exact division and gcd:** as spec 12 ($a = bq$; $a = gx$, $b = gy$; factors at half size), with random directions. Divisors are never zero.

## 5. Measures

For **every build × operation × job**: time per operation; bytes per value (accounted, heap figure beside; Header counts 9 bytes plus the slot, and reports pool capacity not in use separately); peak bytes during the operation. Results are released after the checksum, outside the clock, except in the growth job.

**Timing and verdicts:** spec 12's method, unchanged (idle machine; one pinned core; reps of 50–100 ms; 15 reps; median and spread; Control run twice as the noise; a difference counts only beyond max(5%, noise); every result stored and checksummed after the clock; operand arrays in L1 where they fit; job 1 scalar; callgrind instruction counts beside the times).

**Pairings:** Header × Control in every job; $k$-half × $k$-full within each build; add with random directions × add with directions 1 within each build.

**Known costs, to be measured and reported:**
1. **Rounding up to a power of 2:** up to 2× the work on add and 4× on schoolbook multiply. The $k$-half jobs against $k$-full show it, against these bounds.
2. **Pool management:** allocation, release, growth and move-down. Callgrind's instructions in the pool routines, as a share of the total, and the count of move-downs per operation.
3. **The extra memory read** for a pool number (the pool's base, then the slot). Not isolated; it shows in the gap between job 1 and job 2.
4. **The opposite-direction branches** of add: the add pairing above.
