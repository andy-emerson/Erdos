# M3 peer comparison: M1 against GMP and FLINT

Rule fixed Oct 28, 2026 08:34 CDT (research/m3-rule.md).  This run started at 2026-10-28 09:12:15 and measured first at 2026-10-28 09:14:43; it ended at 2026-10-28 09:58:42.

**Decision rule for M3 (fixed before any measurement: in research/m3-rule.md, and in the header of results/m3.md; the
harness refuses a measured run unless research/m3-rule.md holds this text).**

1. **Rounds.**  Each job runs 12 interleaved rounds.  In every round each row of the job (M1, M1's null copy, and
   each library contender) runs once, as its own process, in an order rotated by one row per round, so the rows of a
   round are paired.  Each invocation runs 3 reps in one process; the first rep (cold) is discarded.  A row's time
   in a round is its **total**: entry (conversion from the raw int64 inputs; for M1 including creating its graph) +
   operation + exit (every result read out in lowest terms as two int64), the minimum of one rep's sum over the
   remaining 2 reps.  Entry is reported separately and is included in the total.
2. **Checks.**  Every result of every invocation is compared with the exact value computed by Python's `fractions`:
   the numerator and the positive denominator in lowest terms must both be equal.  A row that fails any check in any
   round, or is unable, is **n/a** for that job.
3. **Ratio.**  For a contender C, the ratio is **T(C) / T(M1)**, T being the median of the row's per-round totals; above
   1, M1 is faster.  Its 95% interval [lo, hi] is the 2.5th-97.5th percentile of the same ratio over 10,000 bootstrap
   resamples of the rounds (rounds drawn with replacement, the same draw for both rows, so the pairing is kept; seeded).
4. **Null control.**  M1 against its own second copy on the same job, by 3.  The job's **null spread** is
   max(1 - lo, hi - 1, 0) over that interval; the band half-width is **h = max(5%, null spread)**.
5. **Verdict per job and contender:** **faster** (M1 faster) if lo > 1 + h; **slower** (M1 slower) if hi < 1 - h;
   otherwise **tie** (the interval overlaps the band [1 - h, 1 + h]).  **n/a** if either row is n/a or the null control is.
6. **Best library.**  Per job, the best library is the library row (mpq, fmpq, fz where it runs) that passed every
   check with the lowest T.  The job's verdict is M1's verdict against the best library.  (Taking the minimum of two or
   three rows biases this verdict toward the libraries; each library's own verdict is reported too.)
7. **Summary answers.**  (a) **Where is M1 faster than the best library:** the jobs whose verdict is faster.
   (b) **Where is it slower:** the jobs whose verdict is slower.  (Ties and n/a are listed too.)
   (c) **Pay-back of entry, on two axes,** each in two families: **mid** (|num| < 10^6, denominators in [2, 2^20):
   factored by trial division; add and mul alternately, partners at random) and **pq** (|num| < 10^6, denominators p*q
   of two primes in [2^16, 2^31): Pollard rho at M1's entry; add of two values over the same denominator).  Within a
   family the number of operations is fixed and only the axis variable changes.
   - **Axis A, uses per value U** over {1, 3, 10, 30, 100}: each value is an operand of exactly U operations, and each distinct
     denominator is carried by exactly 10 values, so distinct denominators per value stay fixed (1/10) and the
     pool of denominators grows with the number of values.
   - **Axis B, uses per distinct denominator V** over {2, 6, 20, 60, 200}: each value is an operand of exactly one operation, and
     each distinct denominator is carried by exactly V values (so used V times).
   On each axis and family, M1's entry cost **pays back from** the smallest grid value x at which the verdict is faster
   at x and at every larger value of the grid; it reaches **parity from** the smallest such x with tie or faster.  If the
   verdict at the largest value is not faster (resp. tie or faster), the answer is "not within the grid".  An n/a job
   breaks the run of values above it.
8. **Calibration: each contender gets its best normal use**, chosen on a separate calibration run before the rounds
   (3 invocations of each form, alternating; the form with the lower median total).  For fma and chain jobs: M1's
   array form, V4 (inside pg_expr_begin / pg_expr_end) or V3 (each call reduced on its own), used by M1 and its null
   copy alike; and FLINT fmpq's form of a*b + c, fmpq_mul + fmpq_add or fmpq_set + fmpq_addmul.  Calibration times are
   reported but carry no verdict.  No other comparison carries a verdict.


**Scope limit.**  Every input, intermediate and result of every workload fits the M1 bounds (numerators in [-2^63, 2^63), denominators below 2^63); the generator checks this for each workload.  GMP and FLINT are arbitrary precision and pay for that generality here; beyond 64 bits M1 reports overflow, so these results say nothing about larger values.

## Simplifications that may bias the results

- Scope: every value fits 64 bits by construction (checked by the generator).  GMP and FLINT handle any size and carry that generality's cost (and FLINT's fmpz keeps values below 2^62 inline, so most of these values never allocate in FLINT, while GMP's always use limbs).  Nothing here measures M1 beyond its bounds, where it reports overflow.
- Allocation: in single-value jobs GMP and FLINT initialise every value inside the timed entry and every result inside the timed op, and clear them untimed, as M1 allocates its values and results in the timed phases and frees them untimed (pg_graph_destroy).  In array jobs GMP and FLINT vectors are initialised once before the reps and reused (as a caller keeping its vectors would), while M1 creates a new graph in every rep's timed entry (with its 576 KiB factor cache) and allocates its arrays inside the timed phases; this favours the libraries in array jobs.  malloc keeps freed memory for every contender (mallopt), so later reps reuse pages.
- Single-value jobs: every contender makes every result a new object (M1 a holder linked into its nodes, GMP and FLINT an initialised mpq / fmpq).  The operation-list indirection (operands by index) is the same for all.
- Best library: the job's verdict uses the minimum over two or three library medians, which is biased low (a row that was lucky in these rounds is chosen more often), so it biases the verdict toward the libraries; each library's own interval and verdict are in the table.
- FLINT fmpq's a*b + c form is calibrated per job; GMP's mpq has one form (mpq_mul + mpq_add).  The fz contender knows the job's shape: it computes the lcm of the inputs' denominators at entry (each distinct denominator below 2^16 once) and runs only where that lcm is below 2^63; it reduces every result at exit (timed).
- Best normal form (rule 8): M1's V3 or V4 array form and FLINT's fmpq form of a*b + c are each chosen per fma and chain job on a separate calibration run; GMP's mpq has one form (mpq_mul + mpq_add), and column sums use V4 only (a sum is one reduction either way).  The calibration's choice is noisy where the two forms are close.
- Compilers: M1 is linked as `make` built it (gcc 13.3, -O3 -march=native); the driver and its inline loops are clang 18 -O3 -march=native; GMP is the distribution's build (CPU-dispatched assembly); FLINT is the native rebuild in /home/claude/flintblas/inst-native.  Different compilers can move a library's times by a few percent.
- Reps: each invocation runs 3 reps in one process and discards the first (cold: page faults, first touches of the inputs and code); the minimum of the last 2 is kept, with warm caches for every contender alike.  Reading the inputs and writing the outputs are not timed.  M1's factor cache and dictionary start empty in every rep (a new graph), so no rep benefits from an earlier one's factoring.
- Checks compare every result of every invocation (all rounds) with Python's fractions, as int64 pairs; a contender's output passes only if equal in lowest terms with a positive denominator.
- Statistics: the bootstrap resamples rounds, so it captures round-to-round noise, not effects shared by every round (machine, compiler, data).  The null band comes from M1's row only, so a library row much noisier than M1 could be called faster or slower where a wider band would say tie.  About 100 comparisons are made without a multiple-comparison correction.  With 12 rounds the median moves in discrete steps.
- The machine has 2 CPUs and other work may run on it (another agent tests in test/fault/); the 1-minute load average is recorded at the start of each round.  Rows of a round are paired and interleaved, so slow-downs that last several invocations hit all rows of a job alike, but short bursts do not.
- Exit is part of the job: every contender delivers each result in lowest terms as two int64.  GMP and FLINT keep their values reduced, so their exit is a copy; M1 keeps an array's dense numerators over the shared D, so its exit (pg_array_to_fracs) reduces each element, a gcd each, and fz reduces each result over D^2 (or D^(K+1)).  A caller that kept M1's array form without reading it out would pay less; the totals here include the read-out.
- Two large primes: M1 factors every new denominator at entry; a p*q whose primes are above 2^16 and not among the 16 most recently seen large primes goes to Pollard rho, whose cost grows with the smaller prime (here up to 2^30 for P-sh/P-ind and 2^31 for the pq reuse families, about 100 us per denominator in the smoke runs, against the README's ~25 us for primes below 2^24).  This is M1 as accepted (the spec bounds that shortcut), not a harness choice, but the prime range drives those jobs' verdicts.  The pq families draw from one pool of 512 primes, so how often a prime recurs grows with the number of distinct denominators.
- Workloads are synthetic: uniform random numerators and denominators from the stated sets.  The mid reuse families pair values at random and alternate add and mul; the pq families add two values over one denominator.
- Cache size changes along the reuse axes for every contender: on axis A the values occupy 600,000 (mid) or 60,000 (pq) slots at U = 1 and 100 times fewer at U = 100, so operands increasingly come from cache as U grows, for M1 and the libraries alike; on axis B the number of values is fixed but M1's graph (nodes, dictionary) shrinks as V grows.  The pay-back answers therefore mix entry amortisation with cache effects.
- Results are not chained back in as operands: every operation of a reuse job reads only entered values and its result is only read out.  Reuse here means reuse of entered values; a workload that fed results into later operations (where M1's results share nodes with their operands) is not measured, except in the array chains.
