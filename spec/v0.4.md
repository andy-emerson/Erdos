### 17.2 The bound (bug fix; item 1)

- **Bound:** a matrix's cells name at most $2rc$ whole numbers. The "+2" of v0.1 §2 is dropped. v0.2 §15.10 item 1 had kept it as headroom for the formerly pre-stored 0 and 1.
- $T_\text{fix} = 2^{\lceil \log_2 (2rc) \rceil} \ge 2rc$.
- **Fill up to 100% is allowed, and the probe always ends.** A build stores at most $2rc$ distinct whole numbers. So when any new value is stored, at most $2rc - 1$ values precede it, and $W \le 2rc - 1 < T_\text{fix}$. At least one slot is therefore empty, and the wrapping probe visits every slot within $T_\text{fix}$ steps. A full table stays an error that is detected and cannot occur (v0.1 §5.3). High fill makes probing slower; it is never an error.
- **Build handle width** $w_{h,\text{build}}$: v0.1 §5.2's fixed rule on the new $T_\text{fix}$, the smallest of 8, 16, 32 with $w_{h,\text{build}} - 1 \ge \log_2 T_\text{fix}$. So a position ($< T_\text{fix}$) is never the empty mark.
- *On the m3 grid* ($n \in \{16, 32, 64\}$; this round's grid is open, §17.15): $T_\text{fix} = 2n^2$, half of m2's, and $w_{h,\text{build}} = 16$.

### 17.3 Build and pack: the compact index table (general improvement; item 2)

**During a build** (an input's `create` and `enter` calls; a result's `create` and its `madd` or `mmul`):
1. **(l), the list,** is allocated at `create` for the worst case: $2rc$ entries of 64 bits. $W$ entries are used.
2. **(h), the index table,** has $T_\text{fix}$ slots of $w_{h,\text{build}}$ bits. Each slot holds the empty mark or a **position in (l)**. It is filled with the empty mark in one step (§17.5).
3. **Store** of a whole number $v$: probe from $h(v)$ (with $t = \log_2 T_\text{fix}$ bits), slot by slot, wrapping. At slot $s$:
   - empty: $v$ is new. Append $v$ to (l) at position $W$, write $W$ into slot $s$, $W \leftarrow W + 1$, and update the widest value (§17.4). The handle is the old $W$;
   - holds position $k$ with $\text{l}[k] = v$: found; the handle is $k$;
   - otherwise: next slot.
4. **A handle is a list position from the start.** So (l) is in **arrival order**: the distinct whole numbers in the order they were first stored. That is the order of entry, numerator before denominator within a cell. This replaces v0.2 §15.4 item 3's slot order.

**The pack**, once the build ends (inside the last `enter`; at the end of `madd` or `mmul`; v0.2 §15.4 item 5), in this order:
1. free (h);
2. narrow (l) and shrink it to $W$ entries (§17.4);
3. if $w_{h,\text{pack}} < w_{h,\text{build}}$, narrow every field in place in one forward pass, then shrink the cells.
   - $w_{h,\text{pack}}$ is v0.2 §15.4 item 3.4's: the smallest of 8, 16, 32 with $2^{w_{h,\text{pack}} - 1} \ge W$.
   - A field's value ($2k + t$) is unchanged; only its width changes. Field $i$'s write ends at byte $(i + 1) w_{h,\text{pack}} / 8 \le (i + 1) w_{h,\text{build}} / 8$, where field $i + 1$ begins, so no field is overwritten before it is read.

**No pack map, no scan of (h), no rewrite of a handle.**

### 17.4 List width (general improvement; item 3)

- (l) is built at 64 bits. The **widest value** stored so far is tracked, as its width in bits with the sign bit included ($\text{bitlen}(v) + 1$, v0.1 §2).
- At the pack, $w$ is the smallest of 8, 16, 32, 64 that holds the widest value.
- If $w < 64$, (l) is **narrowed in place, in one forward pass**: entry $k$ is read from bytes $[8k, 8k + 8)$ and written to bytes $[k w / 8, (k + 1) w / 8)$. The write ends at $(k + 1) w / 8 \le 8(k + 1)$, where entry $k + 1$ begins, so no entry is overwritten before it is read.
- **(l) is always shrunk** to $W w / 8$ bytes, whether or not it was narrowed: at $w = 64$ it drops from $2rc$ entries to $W$.
- **The same rule for every matrix:** inputs, intermediates and results.
  - Inputs are no longer kept at 64 bits (v0.1 §5.4).
  - Intermediates and results no longer start at 8 bits and widen by copy (v0.1 §5.5; v0.2 §15.5 item 3). There is no widening.
- Reads of a packed matrix: $\text{l}[k]$ at width $w$, sign-extended to 64 bits (v0.2 §15.4 item 1, unchanged). An operand may have any of the four widths.

### 17.5 Fill and field writes (general improvement; item 5)

- **(h) is filled in one step** with the empty mark (all ones at every width), not slot by slot.
- **A cell's two fields are written together.** Both whole numbers are stored, the numerator first, then the denominator. Then the two fields are written in one write at the cell's width.
  - This replaces v0.1 §5.7's second paragraph for Packed. There, the numerator's field was written before the denominator's store.
  - That rule existed for a growth's rewrite, which does not arise here: nothing moves a handle during a build.

### 17.6 Operand reads (item 4) and mul's summation (item 11); both general improvements

"mul" here means every matrix multiplication: the mul job's, and the multiply steps of sop ($A \cdot B$, $C \cdot D$) and pos ($S \cdot U$).

**Operand reads (Packed):**
- **The row buffer.** For each row $i$ of the result, row $i$ of the left operand is decoded once, by handle, into the row buffer. It is then reused for that row's $n$ result cells.
  - **Contents:** $n$ decoded cells. Each holds the numerator's magnitude and the denominator (two 64-bit integers), the sign, and whether the two fields name the same handle. That last item is what the read counters need (v0.1 §7.1).
  - **Size:** $n$ times one decoded cell's size in the build (24 bytes each in the current C build).
- **Counting:** a read from the buffer is counted as the by-handle read it replaces. So every read counter (cross reads, K-Q3 reads) equals what by-handle reads would give.
- The buffer is **local to one function** and is **freed before the pack** of the result. It is never stored or returned.
- The right operand's cells, and both operands in addition, are read by handle, as in mh2.
- **No per-width read loops:** each read dispatches on the width, as mh2's reads do.

**mul's summation (both models; the author, Oct 30, 2026).** Each product cell is summed from the left, starting with the first product. This replaces v0.1 §6.2's cell loop:

```text
function cell(i, j)                                 multiplication, Control and Packed
    let s = mul(A[i][0], B[0][j])                   the first product; a temporary
    for t = 1, ..., n - 1
        let p = mul(A[i][t], B[t][j])               a temporary
        let s = add(s, p)                           on two temporaries
    end for
    store s as C[i][j]
end function
```

- There is no $0/1$ start and no `zero_x` addition. A cell makes $n$ multiplications and $n - 1$ additions, not $n$ and $n$. v0.1 §6.2 item 1's sentence "the first addition of each cell is case `zero_x`" no longer holds. At $n = 1$ there is no addition.
- The terms come in the same order as before, so every remaining addition has the same operands as before.
- Control and Packed sum in the same order, so the call-for-call equality holds.
- §17.10 item 4 interrupts this loop on overflow.

### 17.7 gcd (items 6a and 6b)

The shared gcd (`sk_gcd_raw` in the current build) changes in two ways. **Both Control and Packed use it**, so the comparison stays fair.
- Its values are unchanged.
- Its counters are unchanged: a gcd counts once, and its inner steps not at all (08 v0.1 §12.1, I-2).
- So G(Packed)/G(Control) stays exactly 1, call for call.

**The routine, in order** ($u$, $v$ the operands' magnitudes):
1. **Zeros first:** if $u = 0$, return $v$; if $v = 0$, return $u$. So neither operand of a remainder or of the loop below is 0.
2. **6a, one remainder first (special case).**
   - *Condition:* the bit lengths of $u$ and $v$ differ by more than 8.
   - *Path:* replace the larger by the larger mod the smaller. If that is 0, return the smaller. Otherwise go on to step 3 with the pair.
   - *Why it is faster:* the binary method removes the size difference at about one bit per iteration; one division removes it at once.
   - *Where it arises:* chiefly the reduction $\gcd(t, g)$ of the gcd-first sum, where $t$ is large and $g$ divides a denominator.
   - *Exact:* $\gcd(u, v) = \gcd(u \bmod v, v)$ for $v \ne 0$.
   - Under it, 08's G-4 ("the shared gcd is the binary method") reads, for the m4 builds: the binary method, preceded in this case by one remainder.
3. **The binary method**, as 08's: the shared power of two factored out, both operands made odd, and the loop run while $u \ne v$.
4. **6b, ctz of the raw difference (general improvement).** In the loop, the shift is $\text{ctz}(u - v)$, taken on the raw difference (mod $2^{64}$). Inside the loop $u \ne v$, so $u - v \ne 0$ and its ctz is defined. It equals $\text{ctz}(\lvert u - v \rvert)$, since negation keeps the low zero bits. So the shift no longer waits for the min/abs select. It applies to every call.

**Where it lives:** beside the old gcd, with its own pin. In the current build:
- the new header is `lib/vendor08/m4/sk_internal.h`, beside 08's `lib/vendor08/sk_internal.h`;
- its pin is `lib/vendor08/m4/SHA256SUMS`;
- it differs from 08's file in `sk_gcd_raw` only (`lib/vendor08/m4/sk_internal.diff`);
- 08's file and pin are unchanged, and the m4 builds find the m4 header first.

### 17.9 Workloads (item 8)

**Every whole number is drawn the same way**, numerators and denominators alike:
1. Start at 1.
2. For each prime $p$ in the order 2, 3, 5, 7: while `randrange(p) == 0`, multiply by $p$. The test has probability exactly $1/p$. So, before rejection, $P(\nu_p \ge e) = p^{-e}$ and the primes are independent. Step 3's rejection makes the accepted values' exponents dependent.
3. **After all four primes**, if the value exceeds 32767, **reject it and draw it again** from step 1, from the same stream.
4. A numerator is that value with a **random sign**, from `randrange(2)`: 0 gives +, 1 gives −. A denominator is the value itself.
5. Each rational is **reduced to lowest terms**, as before.

**Order of random calls** (the author, Oct 30, 2026), one `random.Random` stream per job, seeded as below, drawing the job's matrices in order ($A$, $B$; in sop and pos $A$, $B$, $C$, $D$):
- for each rational: the numerator's magnitude (step 2, with any rejections of step 3), then its sign, then the denominator's magnitude (with any rejections);
- within one magnitude: the primes in the order 2, 3, 5, 7. For each prime, its draws, until one fails;
- a rejected magnitude is drawn again at once, from the same stream, before the next call;
- then the pool's filling, as below: its duplicate redraws, then one `choice(pool)` for each of the $n^2 - s$ remaining cells, in cell order, then one `shuffle(cells)`. Then the next matrix.

**The two calls** (settled Oct 30, 2026, the coordinator's call): the $1/p$ test is `randrange(p) == 0`, an exact integer probability; the sign is `randrange(2)`, with 0 giving +.

**Pools** (unchanged from rule-m1, `m1_gen.py`): each matrix has a pool of $s = n^2 / \rho$ **distinct** reduced values. A rational whose value is already in the pool is discarded and a whole new rational is drawn (magnitude, sign, denominator). Then the cells are the pool's $s$ values, once each, followed by $n^2 - s$ values each drawn by `choice(pool)`, and the list is shuffled by `shuffle(cells)`. So:
- **the duplicate redraws are part of the call order;**
- they are heavy under this draw, which concentrates on few values (there are only 497 7-smooth numbers up to 32767): a 4096-value pool ($n = 64$, $\rho = 1$) takes about 94,000–96,000 rationals (measured, three seeds);
- **a pool's values are not distributed exactly as steps 1–5.** They follow that draw conditioned on being distinct, which favours rarer values.

**Same seeds** as before, so every model reads the same numbers. Job $j$ is seeded:
- add: $20261029 + j$; mul: $20261029 + 100 + j$ (`m1_common.py`, `job_seed`);
- sop: $20261029 + 200 + j$; pos: $20261029 + 300 + j$ (`m2_common.py`, `job_seed`).

**The generator's Python is pinned** to CPython 3.13.17, the version on this machine, since `randrange`, `choice` and `shuffle` give the same stream from a seed only within a version. Step 0 records the version and refuses another.

 This replaces the earlier draw (uniform numerators, and denominators among the divisors of 720) and the first draft's uniform 1–32767 denominators. Step 0's files will no longer equal m1's or m2's by sha256.

**Facts that follow** (not decisions):
- every value is 7-smooth and at least 1, so no input numerator is 0; zeros arise only from arithmetic;
- v0.2 §15.5 item 8 and rule-m1's Workloads argument that every value fits 64 bits no longer hold. Overflow is handled by §17.10;
- v0.2 §15.5 item 9 (the sharing of $P$, $Q$, $S$, $U$, from the old draw) no longer applies. Their sharing will be reported as measured.

### 17.10 Overflow (item 10)

**The mark is a placeholder for testing, not a solution to overflow.** Overflow has not been worked on yet. The mark only measures how often overflow happens on these workloads. Whatever the real solution becomes will replace it.

**The author's decisions** (Oct 30, 2026), identical in every model:
- An overflow is possible, and how often it happens is useful information. The **job goes on** after one.
- **The record is the mark in the result's cells, plus two counters, "new" and "passed on".**
  - The counters exist only in the counting build.
  - There is no per-cell overflow list, and the record adds no structure.
  - **The driver finds the marked cells by scanning the result after the timed step**, outside the clock.
- The results report the counts **per job, model and operation** as a finding.

*Expected*: two simulations, both at 64 bits on this draw (primes up to 7). Both are **simulated lower bounds**: they use **unpooled** samples, each cell drawn independently rather than from §17.9's pools. Figures are the share of the result's cells marked.
- **The coordinator's sample:** pos at $n = 64$, about 1%; none elsewhere.
- **This spec's sample**, by the second reviewer's method: running sums and products in lowest terms, by Control's case arithmetic (`tc3.c`'s cases) with 08's checks at every step. Four seeds per size, on the m3 grid ($n \in \{16, 32, 64\}$):

  | Set | $n = 16$ | $n = 32$ | $n = 64$ |
  | --- | --- | --- | --- |
  | add | 0 | 0 | 0 |
  | mul | 0 | 0 | 0–0.05% |
  | sop | 0 | 0–0.2% | 0.07–0.39% |
  | pos | 0 | 0–0.29% | 0.54–0.93% |

**Rules:**
1. **The mark** is $0/0$: the whole numbers 0 and 0, with the numerator's sign tag 0 (+), as zero's (v0.1 §5.1). Each model stores it as it stores any cell: Packed stores the whole number 0, hashed and probed like any other, and Control writes the pair $(0, 0)$.
2. **The test for the mark** is $d = 0$ on an operand cell, made when the operand is read (in mul, from the row buffer for the left operand).
   - **Both operands are tested, the left first.** The right operand's $d$ is tested even when the left is the mark.
   - Each test increments **its own counter, "mark tests"**, in every model alike. It is not one of v0.2 §15.2's 10 comparisons, which stay as counted.
   - **A term or cell stopped by a mark makes no arithmetic reads** (no cross reads, no K-Q3 reads, no comparisons).
   - Only stored cells can be marks; a temporary never is.
3. **Addition of matrices:** read and test the two operand cells. If either is the mark, the result cell is the mark, counted **passed on**. Otherwise compute. An overflow in the arithmetic (08's overflow report, v0.1 §11) makes the cell the mark, counted **new**.
4. **Multiplication: term by term**, in §17.6's left-to-right order, $t = 0, \ldots, n - 1$. For each term:
   - read its operands, $A_{it}$ and $B_{tj}$. If either is the mark, the cell is **passed on**, and it stops;
   - compute the product and, for $t \ge 1$, the addition into $s$. An overflow in either makes the cell **new**, and it stops.

   Whichever comes first decides the count. The terms after it are not computed, and their operands are not read: $B$'s cells not by handle, $A$'s not from the row buffer (which already holds all of $A$'s row). The cell is stored as the mark.
5. **Where the marks are found:**
   - **the result** ($C$, or $R$ in sop and pos): the driver scans the model's result **after the clock, in every build**, as part of the read-out. It keeps only the count of marked cells and their indices, in (out), its own read-out array (v0.1 §3; §17.8). The model holds no record of them;
   - **the intermediates** of sop and pos, which are freed inside the timed operation: through the counters in the counting build, and the test build's checks (§17.12). They are never scanned inside the clock;
   - **counts in sop and pos** are given per step and per job.
6. **Measures:**
   - **1 (build) and 6 (stable bytes):** inputs cannot overflow, since every value is at most 32767.
   - **2–5 (time):** every cell is included, marked or not. A marked cell's time is its work up to the stop, plus the store of the mark. The rule for stopping is the same in every model. Storing the mark costs what storing any cell costs in that model. The time of one cell cannot be split out of an operation's. The driver's scan is outside the clock.
   - **7–8 (peaks):** included, since the mark is stored like any cell.
   - **Value checks** (§17.12): a marked cell is left out of the comparison with the exact reference. Instead:
     - **the set of marked cells is checked per cell:** it must match the simulator's and be identical in every model;
     - **the kinds are checked only through the two counts**, in the counting build: "new" and "passed on" must equal the simulator's and be equal between the models. A cell's kind cannot be checked per cell: both kinds leave the same $0/0$, and there is no per-cell list.
   - **Call for call:** included, up to the stop.
   - **Verdicts:** a job with overflow keeps its verdicts, with its counts reported beside them.

**What this amends:**

| Where | Was | Now |
| --- | --- | --- |
| v0.1 §0 item 8, §4, §6.2 item 5, §11 | an overflow is an error; the operation returns an overflow status | the cell is marked and counted (items 1–4); the operation and the job go on |

### 17.14 Instructions to builders and reviewers (replacing v0.2 §15.9's)

> **Build Packed, and Control from a new copy of its source, both with the new gcd, and nothing else.**
> - Size the build table from the bound $2rc$, with $T_\text{fix} = 2^{\lceil \log_2 (2rc) \rceil}$, and allow it to fill. Fill it in one step with the empty mark.
> - The table's slots hold positions in the list. A new whole number is appended to the list, which is allocated for $2rc$ entries of 64 bits, and the handle is its position.
> - Write a cell's two fields together, after storing both whole numbers.
> - Track the widest value. At the end of each build: free the table; narrow the list in place, in one forward pass, to the smallest of 8, 16, 32, 64 bits that holds the widest value, and shrink it; narrow the fields if the packed handle width is smaller.
> - Make no map, no scan of the table and no rewrite of a handle.
> - In every mul, decode each row of the left operand once into a local row buffer, count it in the accounted total, and free it before the pack. Count its reads as the by-handle reads they replace. Read everything else by handle, with no per-width read loops.
> - In both models, sum each product cell from the first product: $n - 1$ additions, with no $0/1$ start.
> - Use the new gcd in both models.
> - On overflow, store the mark $0/0$ and count the cell "new" or "passed on" by §17.10's rules, the same way in both models, and continue the job. Test both operands of a term or cell for the mark, the left first, counting each test as a "mark test". Keep no list of marked cells.
> - Keep v0.1 §6's arithmetic, call for call between the models.
> - Add no other structure, cache, index or shortcut.

A reviewer MUST check:
- the structures of §17.8 and nothing else;
- the bound $2rc$, and fill up to 100% without error;
- (l) in arrival order, handles as positions from the start; no map, no scan, no rewrite;
- the narrowing rule for every matrix, inputs included, and no widening;
- the row buffer: local, decoded once per row, its reads counted as by handle, counted in the accounted peak, freed before the pack;
- the one-step fill and the paired field write;
- the gcd's zero guard and its two changes, and nothing else in it; its own pin; 08's file and pin unchanged;
- Control's new copy differing from `tcm.c` only by the summation and the marking; `tcm.c` unchanged by its pin;
- mul's summation from the first product, with $n - 1$ additions per cell, in both models;
- overflow handled by §17.10's rules, identically in both models, with the job going on and no scan inside the clock;
- call-for-call equality between the models in every step.
