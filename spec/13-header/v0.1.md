# Signed Integers with a Header: Specification v0.1

Nov 1, 2026, revised after review the same day · Records the author's decisions of Nov 1, 2026. Details that follow from them are marked **(coordinator's call)**. Integers on the CPU only. Checked against [`../../RULES.md`](../../RULES.md) and reviewed in [`review-v0.1.md`](review-v0.1.md). Nothing is built or run.

## 1. The representation

Every number is an **8-bit header** and a **64-bit word**, 72 bits. Headers and words are kept in two parallel lists (header $i$ belongs to word $i$), so a header is never padded to 8 bytes.

- **Header:** bits 0–4 the class code $c$; bit 5 spare, always 0; bits 6–7 the direction $d$, a counter mod 4 for $1, i, -1, -i$ (paper v0.7, §2.3). **(Coordinator's call:** the direction is at the top of the byte, so its carry falls off.**)**
- **Word:** always an unsigned magnitude or a slot index.
  - $c = 0$: the word is the magnitude, up to 64 bits.
  - $c = 1, \dots, 31$: the word is a **slot index** (not a pointer) into the pool for width $2^{c+6}$ bits. Every slot in a pool has that width, words lowest first.
- **Canonical form:** each number is in the smallest class that holds it; zero is header 0, word 0.
- **Word size:** $W = 64$ is fixed for this spec. The layout is little-endian, so it is readable as 32-bit halves; nothing at $W = 32$ is run. A GPU form is out of scope: there is no GPU to test on.
- **Directions:** integer operations produce only $d = 0$ and $d = 2$. $i$ and $-i$ are representable, but complex values (sums across axes) are out of scope for a later spec. An add of two nonzero values on different axes is reported as an error; zero has no axis.

## 2. Builds

Two builds, in Nim 2.2.14 with spec 12's flags and binaries, self-contained.

1. **Control** (record). Spec 12's **Growing** build ([`../12-integers/v0.1.md`](../12-integers/v0.1.md) §1.4), made signed by the same header list and direction rules. In Control the class bits are unused and the word is a pointer to Growing's block.
2. **Header** (general improvement). The representation of §1.

**Shared routines.** Growing's routines are refactored once, for both builds: each writes into a destination the caller gives, with room for one extra word; absolute difference (subtract, then negate on the final borrow) returns that borrow; gcd's output is sized so it never writes past its destination. Control wraps them with `malloc`, Header with a slot. Control must still give spec 12's values.

## 3. Operations

Six operations run on **every build and every job, with no exceptions**: add, subtract, multiply, exact division, gcd and compare.

**Header arithmetic**, with $D = \texttt{0xC0}$, on 8 bits (the result class is then ORed in):
- multiply: `(h1 and D) + (h2 and D)`; exact division: `(h1 and D) - (h2 and D)`; negate: `h xor 0x80`;
- add, equal directions: magnitude $m_1 + m_2$, direction `h1 and D`;
- add, opposite directions: magnitude $\lvert m_1 - m_2 \rvert$ with borrow $b$ (1 when $m_1 < m_2$), direction `(h1 and D) + (b shl 7)`;
- subtract: negate the second, then add; gcd: direction 0;
- any zero result gets header 0.

**Compare** returns $-1$, 0 or 1. If the directions differ, the value with $d = 0$ is larger. If both have $d = 0$, compare magnitudes; if both have $d = 2$, compare magnitudes and reverse. Magnitudes compare by class code first, then by words. Directions 1 and 3 are reported as an error.

**Operands.** Each routine reads each operand's own words at its real length: the inline word as one word (length 0 for zero), or the slot up to its top nonzero word. Growing's routines handle unequal lengths, so nothing is widened.

**Result class** (Header). Let $L = \max(c_1, c_2)$. Predicted: equal-direction add $L + 1$; opposite add $L$; multiply $L + 1$; exact division $c_1$; gcd $\min(c_1, c_2)$, or the other's class when one is zero. The routine allocates a slot of the predicted class, computes into it, finds the top nonzero word, and moves the result to the smallest class that holds it (possibly class 0, inline), releasing the slot. A predicted class above 31 is reported as an error.

**Pools** (Header). A table entry per class: base pointer, capacity, next unused slot, free-list head.
- **Release:** values are immutable, and the owner releases a number explicitly, as with Growing's `release`. A class-0 release does nothing; a slot's index is pushed onto its pool's free list, kept in the freed slot's first word, ending in all ones.
- **Allocation:** pop the free list, else take the next unused slot, else grow.
- **Growth:** a pool is created at its first allocation with one slot, and doubles by reallocating and copying when full. **(Coordinator's call.)** Indices stay valid, pointers do not, so an operation allocates its result slot before taking operand addresses. Pools never shrink.

**Structures** (rule 4). Stored: the slot. Temporary: the predicted slot, when the result moves down. Local: Growing's one buffer in division and gcd. The pools take the place of `malloc`. The two parallel lists are one list of numbers laid out in two parts; this is subject to the author's confirmation (§6).

**Special cases**, named and not built: (a) a class-0 by class-0 result held in two registers, taking a class-1 slot only when its high word is nonzero; (b) equal-direction add allocating class $L$ and moving up only on a carry.

## 4. Operands

All from one seeded Python generator, the same for both builds; 1024 operations per operation and job, as in spec 12.
- **Jobs:** one per class, $k \in \{1, 2, 4, 8, 16\}$ words, with bit lengths uniform from $32k + 1$ to $64k$, so rounding up to the class width shows in Header against Control.
- **Directions:** 1 or $-1$ with probability 1/2 each.
- **Exact division and gcd:** as spec 12 ($a = bq$; $a = gx$, $b = gy$; factors at half size), with random directions. Divisors are never zero.
- **Growth workload** (not a job): 64 chains, each from a random one-word value, of 32 steps $x \leftarrow x \cdot y + z$, with $y \ne 0$ and $z$ random signed one-word values. Each intermediate is released inside the clock. It is timed per step on both builds and exercises pool growth, release and reuse. **(Coordinator's call.)**

## 5. Measures

For **every build × operation × job**, and the growth workload: time per operation; bytes per value (accounted, heap figure beside; Header counts 9 bytes plus the slot); peak bytes during the operation. Pool capacity not in use, including a doubling's copy, is reported separately, not in the peak. Results are released after the checksum, outside the clock, except in the growth workload.

**Correctness:** every result is checked against Python's exact value and against Control, value for value. Each Header result is also checked for canonical form: the smallest class, zero as header 0 and word 0, the spare bit 0.

**Timing and verdicts:** spec 12's method, unchanged. Comparisons are Header × Control only.

**Known costs, to be reported:**
1. **Rounding up to a power of 2:** up to 2× the work on add and 4× on schoolbook multiply; it shows in Header × Control per job, against these bounds.
2. **Pool management:** allocation, release, growth and move-down. Callgrind's share of instructions in the pool routines, and move-downs per operation. Job 1 also uses pools: products past 64 bits and carrying adds take class-1 slots.
3. **The extra memory read** for a pool number (the pool's base, then the slot), within Header × Control.
4. **The opposite-direction branches** of add and subtract, which random directions take half the time, within Header × Control.
