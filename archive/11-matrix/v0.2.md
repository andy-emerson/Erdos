## 15. Amendment of Oct 30, 2026: round m2

**Dated Oct 30, 2026, by the author's decisions.** Round m2 changes three things:
- it drops the pre-stored 0 and 1;
- it narrows the rows to TC, Hash-V-fixed, Hash-V-grow-map and a new row, **Hash-V-pack**, the author's favourite, in which the hash table is only a build tool;
- it adds two **expression** job sets, in which intermediate matrices are built, stored and then used as operands.

### 15.1 What changes (approved by the author, Oct 30, 2026)

1. **No pre-stored 0 and 1, in any row.** Every zero and one test is a value comparison, in every row (§15.2).
2. **Rows:**
   - TC;
   - Hash-V-fixed;
   - Hash-V-grow-map;
   - **Hash-V-pack** (new, §15.4);
   - Hash-V-fixed-null, still the copy of Hash-V-fixed.

   **Dropped:** Hash-M-fixed, Hash-M-grow and Hash-V-grow (lookup). With the M rows, the translation $\tau$ goes too (v0.1 §7.2). Every hash row is V (v0.1 §7.1).
3. **Hash-V-pack:** every stored matrix is its cells plus a **packed list** of its distinct whole numbers. A temporary hash table, at $T_\text{fix}$, is used only while the matrix is built (§15.4).
4. **Expressions:** two new job sets over four input matrices $A$, $B$, $C$, $D$: **sum of products**, $A \cdot B + C \cdot D$, and **product of sums**, $(A + B) \cdot (C + D)$ (§15.5).
5. **Four job sets, four runs:** add, mul, sop, pos (rule-m2).
6. **Pairings:**
   - each hash row against TC;
   - Hash-V-pack against Hash-V-fixed, where the only change is packing after the build;
   - Hash-V-grow-map against Hash-V-fixed;
   - Hash-V-pack against Hash-V-grow-map, reported only (rule-m2 item 7).

**Unchanged:** the arithmetic and its cases, gcd-first (v0.1 §6); TC (v0.1 §4); the 64-bit core; the hash function; linear probing; −1 as the empty mark; $C$'s widening by copy (v0.1 §5.5); the order of entry (v0.1 §5.7); grow's start size and trigger (v0.1 §5.6, M-4, M-5); and the map rewrite.

### 15.2 No pre-stored 0 and 1 (approved by the author, Oct 30, 2026)

Every place v0.1 relied on handles 0 and 1 changes as follows:

| v0.1 | m2 |
| --- | --- |
| §0 item 5, §5.3: 0 and 1 at slots 0 and 1 at creation | Every table starts **all empty** (every slot −1). 0 and 1 are stored only when a cell needs them, hashed and probed like any whole number, at whatever slot the probe gives. |
| §5.3, §5.4: a store tests $v = 0$ and $v = 1$ first, with 0 probes | **No such test.** Every store hashes and probes. |
| §5.1: zero is $+0/1$ at handles 0 and 1 | Zero is still $+0/1$, stored by value: the whole numbers 0 and 1, at their own slots. |
| §6.1 item 2, §6.2 item 2: zero, integer and $\pm 1$ tests by handle | **By value.** "$x$ is zero" is $a = 0$; "$x$ is an integer" is $b = 1$; likewise for $y$. The tests use the values that V reads for its cross tests before a case is chosen (DECISIONS M1-D8), so they need **no extra read**. The $\pm 1$ tests are value tests too: "$x = \pm 1$" is $a = b$, comparing the two values read, exactly as TC's `compare()` does (`X.n == X.e`). Since a cell is in lowest terms, $a = b$ holds only when $a = b = 1$. Every row makes the same 10 comparisons (8 in `add(s, p)`), counted as TC counts them, so the tests stay identical call for call. TC: as now. |
| §5.4: $C$ starts at $w = 8$ holding 0 and 1 | $C$, and every result matrix, starts **empty** at $w = 8$. |
| §5.6 item 3: reinsertion from slot 2; the map sends 0 → 0 and 1 → 1 | Reinsertion from **slot 0**. Every used slot is mapped. |
| §2: $K = 2rc + 2$ "plus 0 and 1"; DECISIONS M1-D3: $W$ counts 0 and 1 | $W$ counts the whole numbers actually stored, 0 and 1 among them only when a cell uses them. The bound is $2rc$. For $T_\text{fix}$, see §15.10 item 1. |
| §6.1 item 3: 0 and 1 found by the store's 0/1 test | They are stored like any value. |
| §10 item 7: audits that slots 0 and 1 hold 0 and 1 | Dropped. The audit checks instead that every used slot is found by its own probe sequence and is used by some cell. |

**Effect on the m1 sweep:** each store's $W$ falls by 0, 1 or 2 against m1, wherever 0 or 1 is not otherwise used. Grow's growths may come one store later.

**Flagged:**
- **(l), the packed list, is a new structure**, approved by the author, Oct 30, 2026.
- (h) is the same kind as Hash-V-fixed's (b), held only during a build.
- (p) is the same kind as Hash-V-grow-map's (r): an old-slot → new-position array.

Only one (h) and one (p) exist at a time: each matrix is packed before the next one's build begins (§15.4 item 5). No other structure exists in any row (v0.1 §3, "Nothing else exists"). The driver's input arrays, (in-A), (in-B), (in-C) and (in-D), and the read-out array (out) are as in v0.1 §3.

### 15.4 Hash-V-pack (approved by the author, Oct 30, 2026)

1. **A stored matrix** is (a) its cells and (l) its packed list:
   - (l) holds **exactly $W$ entries** of $w$ bits, with no empty slot, where $w$ is the width the build table had at the end ($A$, $B$, $C$, $D$: 64; a result: its widened width);
   - **a handle is a position in (l)**, $0 \le k < W$;
   - every operation reads its operands only through stored matrices, by handle: the value is $\text{l}[k]$, sign-extended to 64 bits.
2. **Building any matrix**, whether from input or as an operation's result, uses a temporary build table (h) of $T_\text{fix}$ slots, all empty. It is exactly Hash-V-fixed's table: the same hash, probing and widening. During the build the cells hold slots of (h), at the build handle width $w_{h,\text{build}}$ (v0.1 §5.2, fixed rule).
3. **Packing**, once the build is finished:
   1. allocate (l), $W$ entries of $w$ bits, and (p), $T_\text{fix}$ entries of $w_{h,\text{build}}$ bits;
   2. **copy in slot order:** for $s = 0, \ldots, T_\text{fix} - 1$, each used slot's value goes to the next position $k$ of (l), and $p[s] = k$. So the list is (h)'s used slots in slot order;
   3. **rewrite every cell's handle through (p):** field $f$ becomes $2\,p[\lfloor f/2 \rfloor] + (f \bmod 2)$, with the tag kept;
   4. **shrink the handle width** to $w_{h,\text{pack}}$, the smallest of 8, 16, 32 with $2^{w_{h,\text{pack}} - 1} \ge W$;
   5. free (h) and (p).

   **In place** (approved by the author, Oct 30, 2026): steps 3 and 4 are one forward pass over the cells, **in place**. Each field is read at the build width and written at the packed width; since $w_{h,\text{pack}} \le w_{h,\text{build}}$, a field's new place never lies past its old one. If the width shrank, the cells array is then shrunk with `realloc`. So no second cells array exists, and the structure count above holds.
4. **Timing:** a build and its packing are timed with the build. For an input matrix, that is its own **build time** (measure 1, §15.6). For every intermediate and the result, it is the **operation** (measures 2–5).
5. **When the build ends** (approved by the author, Oct 30, 2026):
   - an input matrix is packed inside the `enter` call of its last cell, since the matrix knows its size, so the driver is unchanged;
   - a result is packed at the end of the `madd` or `mmul` call that builds it.

   Each matrix is packed before the next one's build begins.
6. **Every matrix ends packed:** $A$ and $B$ (and $C$ and $D$) after entry, every intermediate before it is used, and the result after the operation. All of them are the same kind of thing.
7. **Expected effect (non-normative, from m1's $W$):**
   - $w_{h,\text{pack}}$ is 8 bits wherever $W \le 128$, which is most stores at $\rho \ge 16$, and 16 bits elsewhere on the sweep;
   - Hash-V-pack's bytes per cell are about 0.15–0.71 of TC's in addition and 0.34–0.82 in multiplication, against Hash-V-fixed's 1.92–2.5 (v0.1 §9).

### 15.5 Expressions (approved by the author, Oct 30, 2026)

**Two new job sets**, over input matrices $A$, $B$, $C$, $D$, all $n \times n$. In these sets $C$ is an input; the result is called $R$.

| Set | Steps, in order | Intermediates |
| --- | --- | --- |
| **sop**, sum of products | $P = A \cdot B$; $Q = C \cdot D$; $R = P + Q$ | $P$, $Q$ |
| **pos**, product of sums | $S = A + B$; $U = C + D$; $R = S \cdot U$ | $S$, $U$ |

1. **Each step is one matrix operation** of v0.1 §6: addition (§6.1) or multiplication (§6.2), with left and right operands as written. Each step builds its result in full and **stores it by the row's own method** before it is used:
   - Hash-V-fixed: a table of $T_\text{fix}$;
   - Hash-V-grow-map: a grown table;
   - Hash-V-pack: packed;
   - TC: its pairs.
2. **Cross tests** (v0.1 §6) are made between the left and right operands' stores, whichever matrices they are (V, by value).
3. **Widths:** inputs are 64-bit. Every intermediate and $R$ starts empty at 8 bits and widens by copy (v0.1 §5.5), so an operand's store may have any width of 8, 16, 32 or 64. Reads sign-extend.
4. **Read-out:** only $R$ is read out, into (out).
5. **Parts** (as §15.6):
   - one **build** per input, $A$, $B$, $C$, $D$ in that order, each its own `create` and entry, row-major;
   - the **operation**: the three steps, **each result's `create` just before its own step**: `create` $P$, then $P = A \cdot B$; `create` $Q$, then $Q = C \cdot D$; `create` $R$, then $R = P + Q$ (likewise $S$, $U$, $R$ in pos). A step's result is finished, and in Hash-V-pack packed, before the next `create`, so **only one build table (h) is alive at a time**;
   - the read-out.
6. **Lifetime of the intermediates** (approved by the author, Oct 30, 2026). Each intermediate is **freed right after its last use**, inside the operation and timed with it: $P$ and $Q$ just after $R = P + Q$; $S$ and $U$ just after $R = S \cdot U$. Freeing a matrix frees all its structures. So sop's and pos's peaks include the intermediates while they are alive, and the end-of-operation figures hold the four inputs and $R$ only ($5n^2$ cells).
7. **The generator** (approved by the author, Oct 30, 2026): $C$ and $D$ are drawn exactly as $A$ and $B$ are (rule-m1, Workloads):
   - the same value distribution: numerators uniform in $[-32767, 32767]$, denominators uniform among the 30 divisors of 720, reduced;
   - the same sharing $\rho$, with $s = n^2/\rho$;
   - each matrix with its own pool.

   One stream per job draws $A$, $B$, $C$, $D$ in that order. Job $j$ of sop is seeded 20261029 + 200 + $j$, and of pos 20261029 + 300 + $j$.
8. **Every intermediate fits 64 bits.** Every denominator divides $720^2 = 518{,}400$.
   - **sop:** $|P|, |Q| \le n \cdot 32767^2$, so in $P + Q$ every term and sum is at most $2n \cdot 32767^2 \cdot 518{,}400 \approx 1.4 \times 10^{17}$ at $n = 128$.
   - **pos:** $|S|, |U| \le 65534$, with numerators at most $65534 \cdot 720 \approx 4.7 \times 10^7$; in $S \cdot U$ every product numerator is at most $2.2 \times 10^{15}$, and every partial sum's term at most $n \cdot 65534^2 \cdot 518{,}400 \approx 2.9 \times 10^{17}$.

   Both are below $2^{63}$ by factors of about 65 and 32. An overflow is still an error and, after the gates, a bug.
9. **Sharing:** $P$, $Q$ and sop's $R$ are nearly unshared at every $\rho$, like m1's product. $S$ and $U$ are shared where $s$ is small against $n$, like m1's sum.

### 15.6 Measures and instrumentation (the author's measures, approved by the author, Oct 30, 2026)

**Headline measures.** Each has its own verdict per pairing (rule-m2 items 7–9). Everything else is reported.

| # | Measure | What it covers | Judged in run |
| --- | --- | --- | --- |
| 1 | **Build time of one matrix from input** | one input matrix's `create`, its entry, its build-time table, its growths (grow-map) and its packing (pack) | every run, on that run's inputs |
| 2 | **Addition time** | the whole operation: `create` of $C$, the addition, and building, widening, growing and packing $C$ | add |
| 3 | **Multiplication time** | likewise, for the multiplication | mul |
| 4 | **Sum-of-products time** | `create` of $P$, $Q$, $R$, and the three steps, with every intermediate and $R$ built (and packed) | sop |
| 5 | **Product-of-sums time** | likewise, for $S$, $U$, $R$ | pos |
| 6 | **Stable-state bytes of one stored matrix** | one finished input matrix after its build and packing, with no temporary left | every run, on that run's inputs |
| 7 | **Peak bytes during addition** | the largest live total during the operation, temporaries included | add |
| 8 | **Peak bytes during multiplication** | likewise | mul |
| — | Peak bytes during sop and pos | likewise | sop, pos: **reported, no verdict** |

Measures 2–5 exclude building the inputs, which is measure 1.

**The driver's clock reads** (the driver still reads the clock only between calls). For each input $X$ in order:
- read the clock;
- call `create(X)` and every `enter` of $X$;
- read the clock.

Then the operation: read the clock; for each step in order, call its result's `create` and then the step's operation call (so only one build table (h) is alive at a time); read the clock. Then the read-out. So each input's build is timed separately, and the result's `create` falls in the operation, not in creation as in v0.1 §8.

**Pooling the inputs** (measures 1 and 6; approved by the author, Oct 30, 2026):
- **Measure 1.** In each round, each input matrix gives one sample: its build time per run (the kept rep's time for that matrix over r). That is 2 samples per round in add and mul ($A$, $B$) and 4 in sop and pos ($A$, $B$, $C$, $D$).
  - A row's figure is the **median of all its samples** in the run: 24 or 48.
  - The ratio is the reference's figure over the row's.
  - The 95% interval resamples **rounds**, with all of a round's samples kept together, so that samples taken under the same conditions stay paired.
  - Per-matrix times ($A$ alone, $B$ alone, …) are also reported, with no verdict.
- **Measure 6.** It is exact, from the counts: **the inputs' stable bytes summed, over their cells summed**. That equals the mean bytes per cell over the input matrices, since all are $n \times n$. The verdict is on this accounted figure. The heap figure per matrix is reported beside it: the heap's growth from just before the matrix's `create` to just after its build, with every temporary freed.

**Peak tracking** (measures 7 and 8, and sop's and pos's peaks; approved by the author, Oct 30, 2026):
- **Accounted peak.** In the memory build, each row keeps a running total of the accounted bytes of every structure alive: every matrix's cells and table or list; (w), (n), (r), (h), (p); TC's arrays. It updates the total at every allocation and free of a structure, and records the largest value from the start of the operation to its end. The verdict is on this figure, per cell, over the operation's cells: every matrix that exists during the operation, the inputs, the intermediates and the result. That is $3n^2$ in add and mul and **$7n^2$ in sop and pos** ($A$, $B$, $C$, $D$, two intermediates, $R$), the same for every row. **A `realloc` that shrinks Hash-V-pack's cells (§15.4 item 3) is an accounting event:** the cells' accounted bytes drop to the packed size at that call.
- **TC's accounted peak, with `tcm.c` unchanged.** TC has no temporaries: its only structures are each matrix's pairs, $16n^2$ bytes, allocated at `create` and freed with the matrix. So its accounted peak is computed from the counts and the driver's call order: the sum of the pairs of every matrix alive. No code is added to `tcm.c`. The hash rows keep their running total in the new m2 source.
- **Heap peak, every row, no source change.** The memory build is linked with `-Wl,--wrap=malloc,--wrap=calloc,--wrap=realloc,--wrap=free`. The wrappers keep the live sum of `malloc_usable_size` and its maximum, with a `realloc` counted as the free of the old block and the allocation of the new. The maximum is reset at the start of the operation. This applies to TC and the hash rows alike, so `tcm.c`, `tc3.c` and the 08 module stay unchanged. The heap peak is reported beside the accounted peak.
- Neither is in the timing build.

**Also reported, no verdict** (approved by the author, Oct 30, 2026):
- total and read-out time;
- the whole job's bytes after creation and at the end;
- the peak during each input's build;
- Hash-V-grow-map's growth peak;
- per matrix: $W$, $T$, fill and $w$;
- for Hash-V-pack: $w_{h,\text{build}}$, $w_{h,\text{pack}}$, list bytes, cells rewritten and the map's bytes;
- per step of an expression: its cases, cross tests and stores.

**Expected** (non-normative, from m1's $W$):
- **Measure 6.**
  - Hash-V-fixed takes 2.25 times TC's bytes per input cell at $n \le 64$ (4-byte cells plus a 64-bit table of $4n^2$ slots: $(4 + 32)/16$) and 2.5 at $n = 128$ ($(8 + 32)/16$).
  - Hash-V-pack takes about 0.13–0.81 of TC's: 2- or 4-byte cells plus $8W/n^2$ bytes of list per cell.
- **Measures 7 and 8.**
  - In multiplication at $n = 128$, $\rho = 1$, TC's peak is $48n^2$ bytes (three arrays of pairs). Per $n^2$:
    - **Hash-V-pack, about 1.7 times TC's.** Its peak comes at the result's packing, when the list (l) is allocated while (h) and (p) are still alive: packed $A$ and $B$, about 9 each (4-byte cells, a list of about 4.9); $C$'s build-width cells, 8; (h), 32; (p), 16; (l), 8. That is about 82.
    - **Hash-V-fixed, about 2.6 times TC's.** Its peak comes at $C$'s widening from 8 to 64 bits, when the old 8-bit table (4) and the new 64-bit one (32) coexist: $A$ and $B$, 40 each (8-byte cells, a table of 32); $C$'s cells, 8. That is about 124.
  - The build table and map make Hash-V-pack's peak well above its own stable state.

### 15.7 Correctness and tests (v0.1 §10)

Approved by the author, Oct 30, 2026:

1. **Against `fractions`:** every cell of $R$ (or of $C$, in add and mul). In sop and pos, also every cell of each intermediate, checked in the test build.
2. **Against the model, exactly:**
   - every table, slot by slot;
   - every growth;
   - for Hash-V-pack: (h) equal to Hash-V-fixed's table of the same matrix, slot for slot, and (l) equal to that table's used slots in slot order;
   - every case count, per step.
3. **Call for call:** every hash row's per-operation arithmetic equals TC's, in every step.
4. **Across rows:**
   - Hash-V-pack against Hash-V-fixed: the same read-out, cases, core counts, $W$ and found/new per store;
   - Hash-V-grow-map against Hash-V-fixed: the same.
5. **Audits:**
   - no slot is reserved; every used slot is found by its own probe sequence and is used by some cell;
   - for Hash-V-pack: (l) has exactly $W$ entries, every cell's handle is $< W$, and every cell's value is unchanged by the packing.
6. **Tests (untimed):**
   - zero, integer and $\pm 1$ cases by value, with 0 and 1 at arbitrary slots, and in a matrix that holds no 0 or no 1;
   - the packing at every $w_{h,\text{pack}}$ (8, 16, 32), including a width that does not shrink;
   - the in-place pass (§15.4 item 3) at every pair of widths;
   - in sop and pos, each intermediate freed right after its last use, and no structure of it left;
   - a packed matrix as an operand of addition and of multiplication, on the left and on the right;
   - both expressions on small matrices, against `fractions`;
   - intermediates of every width as operands;
   - every v0.1 §10 test that does not name the M rows, Hash-V-grow or handles 0 and 1.

### 15.9 Instructions to builders and reviewers (replacing v0.1 §14's, verbatim)

> **Build TC, Hash-V-fixed, Hash-V-grow-map and Hash-V-pack, and nothing else.** No row stores 0 or 1 in advance: every table starts empty, every store hashes and probes, and every zero, integer and one test compares values. Hash-V-fixed's table has $T_\text{fix}$ slots and is never resized. Hash-V-grow-map's grows from 16 slots before it passes half full and rewrites its cells through the slot map. Hash-V-pack builds every matrix in a temporary table of $T_\text{fix}$ slots, then copies the used slots, in slot order, into a list of exactly $W$ entries, rewrites every handle through an old-slot → new-position map, shrinks the handle width to the smallest that holds $W$ positions, and frees the table and the map. Its operations read only lists and cells, by handle. In the expression jobs every intermediate is built and stored by the row's own method before it is used. Keep v0.1 §6's arithmetic, so it equals TC's call for call. Add no other structure, cache, index, hash or shortcut. Change nothing in `../10-interning/` or in the m1 sources and results.

A reviewer MUST check:
- the structure counts of §15.3 and nothing else;
- no reserved slot and no handle test for 0 or 1 in any row;
- Hash-V-pack's list in slot order, with exactly $W$ entries, (h) and (p) freed after each build, and only one of each at a time;
- every intermediate stored before use;
- the call-for-call equality with TC in every step;
- the 08 module and `tc3.c` unchanged.

### 15.10 Further decisions (approved by the author, Oct 30, 2026)

1. **$T_\text{fix}$ unchanged from m1:** $T_\text{fix} = 2^{\lceil \log_2 (2rc + 2) \rceil}$, which is $4n^2$ on the sweep. The "+2" is kept as headroom, not as reserved slots, so the tables, fills and $w_h$ stay those of m1.
2. **The expression grid:** the same $n \in \{16, 32, 64, 128\}$ by $\rho \in \{1, 4, 16, 64\}$, 16 jobs per set (rule-m2).
3. **Intermediates** are freed right after their last use (§15.5 item 6).
4. **Packing in place:** the cells are rewritten and narrowed in place, then shrunk with `realloc` (§15.4 item 3).
5. **An input is packed** inside its last `enter` call; a result at the end of its operation call (§15.4 item 5).
6. **Pooling** of the inputs for measures 1 and 6 (§15.6).
7. **Peak tracking:** the accounted running total and the heap wrapper, in the memory build only (§15.6).
8. **Run order:** add, mul, sop, pos, **back to back**, without waiting for the author between runs (rule-m2).
