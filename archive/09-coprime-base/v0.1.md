## 1. Scope

In scope: Design 2 (the coprime base): its structures, operations, integer width, errors, instrumentation and correctness checks; and the boundary that says what its build contains. The control and the shared-denominator ceiling it was measured against, and the shared integer module and lookup it is built on, are specified in the joint specification ([§4.3](../partial-sharing-baseline/v0.1.md#43-width-and-integer-routines), [§5](../partial-sharing-baseline/v0.1.md#5-shared-structures-the-lists-the-lookup-and-store), [§6](../partial-sharing-baseline/v0.1.md#6-the-control), [§9](../partial-sharing-baseline/v0.1.md#9-the-shared-denominator-ceiling)); the requirements they share with Design 2 are repeated here.

Out of scope: performance targets, the workloads and the measurement rule (in the baseline's [`research/rule.md`](../partial-sharing-baseline/research/rule.md)), comparison, printing and parsing, threads, and widths other than 32 and 64 bits.

## 2. Conformance language

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are to be interpreted as described in RFC 2119 when, and only when, they appear in capitals. Sections or paragraphs marked *non-normative* state no requirement.

## 3. Terms and notation

- **Width** $w$: the number of bits of every full-width integer, 64 or 32 (§4.3).
- **Value.** A rational $m/d$ with numerator $m$ and denominator $d \ge 1$. **Lowest terms:** $\gcd(m, d) = 1$, the sign on $m$, and $d > 0$. Zero is $0/1$.
- **Class.** One set of values that share structures. A program creates a class, enters values into it, and applies operations to values of the same class.
- **Handle.** The position of a value in its class's value list: a 32-bit unsigned integer.
- **Index.** A position in a list, a 32-bit unsigned integer. Denominator index $k$ means the same denominator in every structure of a class.
- **Stored.** A value is stored when it is appended to its class. A stored value is never changed. Every result is stored as a new value.
- **Entry.** Storing a value given from outside as an integer pair $(m, d)$. **Operation:** add, subtract, multiply or divide, on two stored values, storing the result.
- **Residual** of $d$ at a divisor $c$: $d / c$.
- **Piece**, **coprime base**, **valuation** $\nu_q(d)$: as in the coprime-base note. The pieces of a coprime base are pairwise coprime integers greater than 1, and $d = \prod_q q^{\nu_q(d)}$.
- **Gcd-first method:** reduced-rational arithmetic that takes the gcd of the two denominators before forming the sum, and takes cross gcds before forming a product (§6).
- $\text{bits}(x)$ is the number of bits of $|x|$; $\text{bits}(0) = 0$.

## 4. Requirements on every implementation

### 4.1 Interface

Design 2 MUST provide, as the control and Design 1 do (joint §4.1):

| Call | Effect |
| --- | --- |
| `create()` | a new, empty class |
| `destroy(class)` | frees the class and everything in it |
| `enter(class, m, d)` | stores $m/d$ in lowest terms; returns its handle, or an error |
| `add`, `sub`, `mul`, `div` `(class, x, y)` | stores the result of $x \circ y$; returns its handle, or an error |
| `read(class, x)` | returns the numerator and denominator of $x$, in lowest terms |
| `size(class)` | the number of stored values |
| `memory(class, report)` | fills the memory report of §12.2 |
| `counters(class, report)` | fills the counters of §12.1 (counting build) |
| `audit(class)` | the **full audit**: checks every invariant of §13.2; returns pass or the first failure (test build) |
| `audit_changed(class)` | the **incremental audit** of §13.2: checks only what changed since the last audit; returns pass or the first failure (test build) |
| `audit_scheduled(class)` | the full audit as §13.3 item 2 schedules it before the last call: in Design 2 with more than 1,024 pieces, pairwise coprimality is checked only for pieces created or rewritten since the last audit, against every other piece, and every other invariant in full; on every other row, and in Design 2 at or below 1,024 pieces, the same as `audit` (test build) |

*Amendment, Oct 28, 2026:* `audit_scheduled` is added (library DEC-2). §13.3's large-base rule changes every scheduled full audit except the last, which `audit(class)` cannot tell apart; `audit` stays the complete audit and is the one run after the last call.

### 4.2 Values

1. Every stored value MUST be in lowest terms, with the sign on the numerator and a positive denominator.
2. Zero MUST be stored as $0/1$, whatever operation produced it.
3. Subtraction MUST be computed as addition of the negated second operand: $x - y = x + (-y)$. Negation changes no denominator.
4. `enter` MUST move the sign of $d$ to $m$ and reduce $m/d$ by $\gcd(m, d)$ before storing.
5. A stored value MUST NOT be modified, moved to another handle, or freed before its class is destroyed.

### 4.3 Width and integer routines

1. Every full-width integer (numerators, denominators, pieces, remainders, residuals, intermediates) MUST have one width $w$, chosen by a single build setting. The default MUST be 64; 32 MUST be supported by a rebuild with no change to source.
2. Numerators MUST lie in $[-(2^{w-1} - 1),\ 2^{w-1} - 1]$ and denominators in $[1,\ 2^{w-1} - 1]$. The most negative integer is excluded, so negation and absolute value never overflow.
3. An implementation MUST NOT use an integer wider than $w$ for any full-width intermediate. The lookup hash and index arithmetic (positions in lists and rows, and the small numbers $\nu_q$) are not full-width arithmetic: the hash MUST use unsigned 64-bit wrapping arithmetic at every width, including $w = 32$ (§5), and positions MUST use unsigned integers of at least 32 bits.
4. All implementations MUST use one shared module of integer routines, and no other full-width arithmetic:
   - **gcd**: the binary method (removing common factors of 2 by counting trailing zeros, then subtracting), on magnitudes, with $\gcd(a, 0) = |a|$;
   - **checked add, subtract and multiply**, each reporting overflow (§4.4);
   - **exact division** of $a$ by a known divisor $b$ (the hardware divide);
   - **division with remainder** (the hardware divide), used for divisibility tests;
   - **bit routines**: popcount, highest set bit and trailing zeros of a 64-bit word, and $\text{bits}(x)$.
5. In the counting build (§12.1), every routine of item 4 MUST count its calls, by the counting rules of §12.1.

### 4.4 Overflow

1. Every full-width addition, subtraction and multiplication MUST be checked. A result outside the ranges of §4.3 item 2 MUST be reported as overflow. Overflow MUST NOT wrap silently.
2. On overflow the operation MUST return the overflow error, store no value, and record where it happened: the operation, the handles of its operands, and the step (named as in the pseudocode).
3. The class MUST remain valid after an overflow: every invariant of §13.2 holds. Changes made before the overflow that change no stored value (Design 2's splits) MAY remain.
4. The harness excludes a trial that reports any overflow from the comparisons. The measurement rule's workloads make overflow impossible, so it treats such an overflow as a bug (the rule says how).

### 4.5 Errors

1. `enter` with $d = 0$, and `div` with $y = 0$, MUST return the division-by-zero error and store nothing.
2. A handle not in the class MUST return the invalid-argument error.
3. Out of memory MUST print a message and abort.
4. Exceeding the limits of §14 MUST abort with a message.

### 4.6 Language and build

1. Each implementation MUST be written in C (C11), single-threaded, with no library beyond the C standard library.
2. All implementations MUST be compiled by the same compiler with the same flags.
3. There MUST be three builds of the same source, differing only in compile-time settings:
   - the **timing build**: counters and audits compiled out;
   - the **counting build**: counters compiled in, audits out;
   - the **test build**: counters and audits compiled in.
4. Counters and audits MUST NOT change the control flow or the results of any operation.

## 5. Shared structures: the lists, the lookup and `store`

Design 2 MUST keep the following three structures, as Design 1 does. The control keeps only a value list (joint §6), and the ceiling its vectors (joint §9).

| Structure | Shape | Each entry stores |
| --- | --- | --- |
| Numerators | list of $N$ | the numerator ($w$ bits) and its denominator index (32 bits) |
| Denominators | list of $D$ | the denominator ($w$ bits) |
| Lookup | array of $S$ slots | a denominator index, or empty |

1. **Lists.** A list MUST only grow at its end. An index, once given, MUST refer to the same entry for the life of the class. A handle is a position in the numerator list.
2. **Lookup.** The lookup MUST be a hash table of denominator indices with linear probing:
   - $S$ is a power of two, initially 16;
   - before an insertion would make the table more than half full, $S$ MUST double and every index MUST be placed again, in index order;
   - the starting slot of a value $v$ is $\lfloor (v \cdot \phi \bmod 2^{64}) / 2^{64 - \log_2 S} \rfloor$ with $\phi = \text{9E3779B97F4A7C15}_{16}$, computed with unsigned 64-bit wrapping arithmetic at every width, including $w = 32$ (this is index arithmetic, not a full-width operation, is allowed by §4.3 item 3, and is not overflow-checked);
   - a probe reads the index in a slot and compares the denominator list's value at that index; a slot holds an index, never a value; the search moves to the next slot, wrapping at the end, until it finds the value or an empty slot.
3. **Fast path.** When two operands have equal denominator indices, an operation MUST take the same-denominator path given in its pseudocode.

The procedure `store(n over e)` appends a result:

```text
function store(n over e)
    if n is 0 then
        set e to 1
        set R to empty, L to empty and u to 1                       §8.3
    end if
    look e up
    if e is found at index k then
        append (n, k) to the numerators
    else
        append e to the denominators as index k
        place k in the lookup
        create the structures of the new denominator k        §8.3, from R, u and L
        append (n, k) to the numerators
    end if
    return the handle of the new numerator
end function
```

The operation passes, with $n$ and $e$, what it knows about $e$ (§8.3): the known row $R$, the remainder $u$, and, from addition, subtraction and multiplication with different indices, the list $L$ of tested pieces, from which `finish` completes $R$ and $u$. `store` refines nothing. When the lookup finds $e$, they are discarded, `finish` is not run, and nothing is added to the existing row; they are used only to build the structures of a new denominator.

## 8. Design 2: the coprime base

*Amendment, Oct 29, 2026, approved by the author: refinement on demand.* §8.1–§8.6 replace the eager form, and §8.7 is added. The eager form refined every new denominator against the whole base as soon as it was stored, whether at entry or as a result. That cost up to $C$ gcds per new denominator: the pilot found 4–11 million gcds per mixed job, against the control's 31–47 thousand ([finding](research/eager-d2-finding.md)).

In the on-demand form:
- each row holds a **known part** and an **unrefined remainder** $u$;
- entry and `store` compute no gcd against the base;
- two rows are refined only when their denominators **meet**, in an addition, a subtraction or a division, and only as far as that operation needs.

**Principle: no work in advance, no work in the background; each operation computes only what it needs.**

The base stays pairwise coprime, and every stored value is the same as before. The earlier text of §8.1–§8.6 is superseded, not kept.

Design 2 MUST keep six structures.

### 8.1 Structures

| Structure | Shape | Each entry stores |
| --- | --- | --- |
| Numerators, denominators, lookup | §5 | §5 |
| Base | list of $C$ | a piece ($w$ bits); pieces pairwise coprime, each greater than 1 |
| Exponent rows | one array per denominator, of varying length | (piece index, $\nu_q$) pairs, 32 bits each, sorted by piece index: the **known part** of $d$ |
| Remainders | list of $D$ | $u_k$ ($w$ bits): the **unrefined remainder** of $d_k$ |

1. **Known part and remainder.** Write $K_k = \prod_q q^{\nu_q(K_k)}$ over row $k$. Then $K_k \cdot u_k$ MUST equal $d_k$, every $\nu$ stored MUST be at least 1, and $u_k \ge 1$. The row of $d = 1$ is empty, with $u = 1$.
2. **The remainder is unrestricted.** $u_k$ MAY share factors with any piece, including a piece of its own row. So a row's $\nu_q(K_k)$ equals $\nu_q(d_k)$ only where $u_k$ is coprime to $q$. A meeting establishes that where its operation needs it (§8.2).
3. The skeleton keeps no list of which rows use a piece. A split MUST scan every row.
4. Pieces are never removed. A piece enters the base only in a meeting (`absorb`, §8.2), and changes only by a split. When a piece splits, the first new piece takes its index and the others are appended to the base.

### 8.2 Meetings and refinement

`meet(i, j)` is called by addition, subtraction and division with different indices, on the two operand rows, before the walk. Each remainder is refined against the other row's pieces and against the other remainder. On return:
- **(M1)** $u_i$ is coprime to every piece of row $j$;
- **(M2)** $u_j$ is coprime to every piece of row $i$;
- **(M3)** $\gcd(u_i, u_j) = 1$.

Each condition refers to the rows as they are on return, including any piece they gained during the meeting.

```text
function meet(i, j)                                       i is not j
    if u_i is 1 and u_j is 1 then
        return
    end if
    set queue A, for u_i, to the pieces of row j
    set queue B, for u_j, to the pieces of row i
    repeat
        while queue A or queue B has a piece not yet taken do
            take the next piece q, from A while A has one, otherwise from B
            if the remainder of q's side is not 1 then
                reduce(that side, q)
            end if
        end while
        if u_i is 1 or u_j is 1 then
            return
        end if
        set g to gcd(u_i, u_j)
        if g is 1 then
            return
        end if
        absorb(g)
    end repeat
end function

function reduce(side k, q)                                 refine u_k against the piece q
    while u_k is not 1 do
        set h to gcd(u_k, q)
        if h is 1 then
            return
        else if h is q then
            divide u_k by q as many times as it goes, counting n
            add n to ν_q in row k
            if row k did not hold q before then
                add q to the other side's queue           the extra refinement
            end if
        else
            split(q, h)                                    the first new piece takes q's index; stay at it
        end if
    end while
end function

function absorb(g)                                         g = gcd(u_i, u_j) > 1
    set rest to g
    set p to 0                                             the scan position
    while rest is not 1 and p is below C do                C is read at each test: splits append pieces
        set q to piece p
        set h to gcd(rest, q)
        if h is 1 then
            set p to p + 1
        else if h is q then
            divide rest by q as many times as it goes
            add q to both queues
        else
            split(q, h)                                    the first new piece takes index p
        end if
    end while
    if rest is not 1 then
        append rest to the base as a new piece
        add it to both queues
    end if
end function

function split(q, g)                                       1 < g < q, g divides q
    set P to the coprime base of {g, q / g}, by pair refinement
    sort P in increasing order
    for each piece s in P do
        set ν_s(q) to the number of times s divides q
    end for
    the first piece of P takes q's index; append the others to the base
    for each row that holds the entry (q, t) do
        replace that entry by the entries (s, t · ν_s(q)) for s in P
        keep the row sorted by piece index
    end for
    for each queue of the meeting that holds q, taken or not do
        add the other pieces of P to it
    end for
end function
```

A split happens only inside a meeting, which runs before the operation builds its result's row $R$, so $R$ is empty during every split and is not visited (*clarified Oct 29, 2026:* an earlier text listed "the row $R$ being built", which no split can reach).

1. **Pair refinement** of a list: while two entries $a$, $b$ have $h = \gcd(a, b) > 1$, replace them by $h$, $a/h$ and $b/h$; drop entries equal to 1 and merge duplicates. It uses gcds and exact divisions only. Refinement MUST NOT factor any number.
2. **Refinement happens only in a meeting.** Entry, `store`, multiplication and the same-index paths MUST NOT test a remainder or a new denominator against a piece. Only `meet` refines, and it refines only the two rows that meet and, through splits, the rows that hold a split piece.
3. **The extra refinement.** A piece that `reduce` adds to a row that did not hold it MUST be added to the other side's queue. The other remainder was refined against that row's pieces as they were, not against the pieces the row gains during the meeting, so without this step M1 or M2 can fail. *Counterexample* (non-normative; a unit test, §13.3):
   - $\tfrac{1}{2} + \tfrac{1}{6} = \tfrac{2}{3}$;
   - then $\tfrac{1}{2} \div \tfrac{2}{3} = \tfrac{3}{4}$ stores row $4$ as $\{2{:}1\}$ with $u = 2$;
   - in $\tfrac{3}{4} + \tfrac{1}{8}$, queue A for $u_4$ is empty, since row $8$ has no pieces, and queue B for $u_8$ holds $2$, so $u_8$ becomes $1$ and row $8$ becomes $\{2{:}3\}$.

   Only the extra refinement then tests $u_4 = 2$ against $2$. Without it, the walk takes $r_x = 2$, $r_y = 4$ and stores $14/16$, which is not in lowest terms; with it, row $4$ becomes $\{2{:}2\}$, $u_4 = 1$, and the result is $7/8$.
4. **Staying at a piece.** `reduce` stays at $q$ after dividing by it, since the remainder may still share part of $q$: $u = 12$ against $q = 6$ leaves $2$, which then splits $6$. After a split, it stays at $q$'s index, which now holds the first new piece; the other new pieces join the queue. `absorb` is one scan of the base, with the same rules: it MUST NOT restart at piece 0, it stops as soon as `rest` is 1, and the gcd it finds is the one used, never computed a second time (§15.1).
5. **Queues.** A queue MUST NOT hold a piece twice. A remainder of 1 is not tested. Queue A is emptied before each piece taken from queue B. The gcd of the two remainders is taken only when both queues are empty and both remainders exceed 1; after an `absorb`, the queues run again.
6. A meeting changes the known parts and remainders of rows $i$ and $j$, and, through splits, the known parts of the rows that hold a split piece. It MUST NOT change any stored value.
7. **No record of meetings.** Nothing records that two rows have met. A later meeting of the same pair tests the remainders again, and finds nothing new. A record of met pairs is outside the skeleton (§10).

### 8.3 New denominators

When `store` adds a new denominator $e$, its row MUST be $R$ and its remainder $u$, as the operation or entry passes them. **No refinement is done.** Addition, subtraction and multiplication with different indices also pass the list $L$ of the pieces they tested for cancellation. Only for a new denominator, `store` first completes $R$ and $u$ with `finish(R, L, u)`:

| Source | $R$ | $u$ |
| --- | --- | --- |
| entry | empty | $e$ |
| addition and subtraction, different indices (§8.4) | the known valuations: $\max(\nu_q(K_i), \nu_q(K_j))$ where they differ; then, by `finish`, $a - k$ at each tested piece whose cancellation is $q^k$ | $u_i u_j$, times, by `finish`, each **leftover** $q^a / h$, for each tested piece whose cancellation $h$ is not a power of $q$ |
| addition and subtraction, same index | empty | $e = d_i / h$ |
| multiplication, different indices (§8.5) | the known valuations: $a + b$ at the pieces in both rows; then, by `finish`, $n - k$ at each tested piece whose cancellation is $q^k$ | $(u_i / h_i)(u_j / h_j)$, the remainders less their cancellations, times, by `finish`, each leftover $q^n / h$ |
| multiplication, same index | row $i$ with every $\nu$ doubled | $u_i^2$ |
| division, different indices (§8.6) | the valuations of $K_i / \gcd(d_i, d_j)$ | $u_i \cdot t / g_1$ |
| division, same index | empty | $t / g_1 = e$ |
| a zero result (§5) | empty | $1$ |

```text
function finish(R, L, u)                                L: entries (q, n, p, h), p = q^n, h = gcd of p and the numerator
    for each (q, n, p, h) in L, in piece order do
        set k to power(h, q)
        if k is not none then
            add (q, n − k) to R if n − k > 0             keeping R sorted by piece index
        else
            multiply u by p / h                          a leftover: q is composite
        end if
    end for
    return (R, u)
end function

function power(h, q)                                    k if h = q^k, otherwise none
    set k to 0
    while h is not 1 do
        divide h by q with remainder
        if the remainder is not 0 then
            return none
        end if
        set h to the quotient and k to k + 1
    end while
    return k
end function
```

1. **Lookup first.** The test "$h$ is a power of $q$" matters only for building a new row, so it MUST be made in `finish`, after the lookup, and only when the lookup does not find $e$. When the lookup finds $e$, no power test is made (§15.1).
2. **$h = 1$ costs no division.** `power(1, q)` returns $0$ without dividing: $h = 1$ is $q^0$, recognized by one comparison. For $h = q^k$ with $k \ge 1$, `power` makes exactly $k$ divisions with remainder. When $h$ is not a power of $q$, it makes one more, the failing one, after its successful ones.
3. `finish` and `power` run inside `store`, and are counted there (§12.1).
4. **The remainder divides $e$.** Each product of remainders in the table divides $e$, which the operation has already formed and checked (§8.7). So it cannot overflow, and a factor 1 is not multiplied.

Every operation with different indices reuses the valuations it already knows. They are a direct output of its own arithmetic, so a production coprime-base implementation would keep them, and the author's ruling allows it (§15.2). Design 1 has no counterpart: its new rows hold divisor 1 only ([its §7.4](../08-common-divisors/v0.1.md#74-new-denominators-islands)). When the lookup finds the denominator, its existing row is used, and $R$, $L$ and $u$ are discarded: nothing is added to the existing row.

### 8.4 Addition and subtraction

```text
function add(m_x over d_i, m_y over d_j)
    if i is j then
        set t to m_x + m_y
        set h to gcd(t, d_i)
        return store((t / h) over (d_i / h)), with R empty and u = d_i / h
    end if
    meet(i, j)                                            §8.2
    set r_x to u_i, r_y to u_j, R empty, "equal" empty and L empty
    walk rows i and j together; for each piece q with a = ν_q(K_i) and b = ν_q(K_j) do
        multiply r_x by q^(a − min(a, b))
        multiply r_y by q^(b − min(a, b))
        if a equals b then
            add (q, a, q^a) to "equal"                    a is not 0: the walk visits only pieces of a row
        else
            add (q, max(a, b)) to R
        end if
    end walk
    set t to m_x · r_y + m_y · r_x
    set e to d_i · r_y
    for each (q, a, p) in "equal" do
        set h to gcd(t, p)
        if h is not 1 then
            divide t by h, and e by h
        end if
        add (q, a, p, h) to L                             the power test waits for the lookup
    end for
    return store(t over e), with R, L and u = u_i · u_j   finish(R, L, u) runs only for a new denominator
end function
```

1. A power $q^n$ MUST be formed by repeated multiplication, once per piece and call.
2. Only the pieces with $\nu_q(K_i) = \nu_q(K_j) > 0$ are tested. When there are none, no gcd is computed after the meeting.
3. "$h$ is $q^k$" is tested by `power`, inside `finish`, only after the lookup has not found $e$ (§8.3). The result's known valuations come from the walk: $\max(a, b)$ where $a \ne b$, and $a - k$ where $a = b$ and $h = q^k$. They MUST be reused (§15.2). A zero sum gives $h = p$ at every equal piece; `store` then stores $0/1$ with $R$ and $L$ empty and $u = 1$, and runs no `finish` (§5).

### 8.5 Multiplication

```text
function multiply(m_x over d_i, m_y over d_j)
    if i is j then
        return store((m_x · m_y) over (d_i · d_i)), with R = row i with every ν doubled and u = u_i · u_i
    end if
    set R empty, L empty, g_1 to 1, g_2 to 1                no meeting
    walk rows i and j together; for each piece q with a = ν_q(K_i) and b = ν_q(K_j) do
        if a > 0 and b > 0 then
            add (q, a + b) to R                           nothing can cancel
        else
            if b > 0 then
                set (m, n, G) to (m_x, b, g_1)            a piece of d_j only
            else
                set (m, n, G) to (m_y, a, g_2)            a piece of d_i only
            end if
            set p to q^n
            set h to gcd(m, p)
            divide m by h, and multiply G by h            in place: m_x or m_y, g_1 or g_2
            add (q, n, p, h) to L                         the power test waits for the lookup
        end if
    end walk
    set u'_i to u_i and u'_j to u_j
    if u_i is not 1 then
        set h to gcd(m_y, u_i)
        divide m_y and u'_i by h, and multiply g_2 by h   skipped when h is 1
    end if
    if u_j is not 1 then
        set h to gcd(m_x, u_j)
        divide m_x and u'_j by h, and multiply g_1 by h   skipped when h is 1
    end if
    set e to (d_i / g_2) · (d_j / g_1)
    return store((m_x · m_y) over e), with R, L and u = u'_i · u'_j
end function
```

1. Here $m_x$ and $m_y$ have already been divided by $g_1$ and $g_2$.
2. **No meeting is needed.** Multiplication needs only $g_1 = \gcd(m_x, d_j)$ and $g_2 = \gcd(m_y, d_i)$. Taking $\gcd(m_y, \cdot)$ over the factors of $d_i$ one at a time, and dividing $m_y$ as it goes, gives $\gcd(m_y, d_i)$ exactly, even where $u_i$ shares factors with row $i$'s pieces. At each prime, the sequence takes $\min(\alpha, \beta)$ and then $\min(\alpha - \min(\alpha, \beta), \gamma)$, which sum to $\min(\alpha, \beta + \gamma)$.

   A piece in both rows is skipped, because $m_x$ is coprime to $d_i$, and so to every piece of row $i$; likewise $m_y$ for row $j$. Both rows are left unchanged.
3. "$h$ is $q^k$" MUST be tested by `power` (§8.3), inside `finish`, only after the lookup has not found $e$: $h = 1$ is $q^0$ with no division; otherwise $h$ is divided by $q$ while the remainder is 0, stopping when it reaches 1.
4. **A composite piece.** When $h$ is not a power of its piece $q$, the leftover $q^n / h$ joins the result's remainder; the piece is not split until that remainder meets a row holding it. (Base $[6]$, from the meeting of $6$ and $36$: in $\tfrac{2}{1} \cdot \tfrac{1}{6}$, $h = \gcd(2, 6) = 2$ is not a power of $6$. $R$ is empty, and the row of $3$ is stored with $u = 3$. A later $\tfrac{1}{3} + \tfrac{1}{6}$ meets row $6$ and splits $6$ into $2$ and $3$.)

### 8.6 Division

```text
function divide(m_x over d_i, m_y over d_j)
    if m_y is 0 then
        fail with division by zero
    end if
    set s to the sign of m_y and t to |m_y|
    set g_1 to gcd(m_x, t)
    if i is j then
        return store((s · (m_x / g_1)) over (t / g_1)), with R empty and u = t / g_1
    end if
    meet(i, j)                                            §8.2
    set r_x to u_i, r_y to u_j, and R empty
    walk rows i and j together; for each piece q with a = ν_q(K_i) and b = ν_q(K_j) do
        multiply r_x by q^(a − min(a, b))
        multiply r_y by q^(b − min(a, b))
        if a > min(a, b) then
            add (q, a − min(a, b)) to R
        end if
    end walk
    return store((s · (m_x / g_1) · r_y) over (r_x · (t / g_1))), with R and u = u_i · (t / g_1)
end function
```

Only $t / g_1$, part of the old numerator, is new, and it joins the remainder unrefined.

### 8.7 Why the walk is exact (non-normative)

After `meet(i, j)`, let $p$ be a prime dividing both $d_i$ and $d_j$:
- $p$ does not divide $u_i$. Otherwise, by M3, $p$ would not divide $u_j$, so it would divide a piece of row $j$, which M1 forbids.
- Likewise, $p$ does not divide $u_j$.

So $p$ divides a piece of row $i$ and a piece of row $j$, and since the base is pairwise coprime, it is the same piece $q$. Hence:
- at a piece $q$ in both rows, $\nu_p(d_i) = \nu_q(K_i)\, \nu_p(q)$, and likewise for $d_j$;
- a piece in one row only, and that row's remainder, are coprime to the other denominator.

So $\gcd(d_i, d_j) = \prod q^{\min(a, b)}$ over the shared pieces, and the residuals are
$$
r_x = u_i \prod_q q^{a - \min(a, b)}, \qquad r_y = u_j \prod_q q^{b - \min(a, b)}.
$$
The sum can cancel only at pieces of equal valuation, exactly as without remainders.

The result's remainder $u_i u_j$ divides $e = d_i r_y / h$ (§8.3 item 4): $u_i$ divides $d_i$ and $u_j$ divides $r_y$, and $h$ divides the product of the equal pieces, which by M1 and M2 is coprime to both remainders. In division, $u_i$ divides $r_x$, so $u_i \cdot t/g_1$ divides $e = r_x \cdot t / g_1$.

Without the extra refinement (§8.2 item 3), M1 or M2 can fail for a piece gained during the meeting, and the gcd read off the rows is then too small.

## 9. The shared-denominator ceiling

The ceiling, a reference point for workloads in which every value shares one denominator, is specified in the joint specification, [§9](../partial-sharing-baseline/v0.1.md#9-the-shared-denominator-ceiling). Not part of this specification.

## 10. The skeleton's boundary

Each build MUST be an accurate representation of the skeleton: the plainest correct form of the design. Bugs and plain inefficiencies inside the skeleton are fixed. Nothing outside it is added.

**Inside the skeleton:**
- one fixed integer width, 64 bits, set in one place, with overflow detected; schoolbook arithmetic;
- the same gcd and division routines as in Design 1, the control and the ceiling;
- the denominator lookup: a hash table of indices, with linear probing, growing when half full;
- Design 2's meetings (§8.2): refining the remainders of the two rows that meet, against each other's pieces and each other, with the extra refinement, and `absorb`'s one scan of the base for a common factor of the remainders;
- **result reuse in Design 2 only:** a new result denominator's row starts from the valuations the operation's own arithmetic computed, and only the unknown part is refined (§8.3) (Design 1 has none, under the ruling R-1, §15);
- **no work in advance, no work in the background; each operation computes only what it needs** (as in Design 1).

**Outside the skeleton** (possible later improvements, MUST NOT be built):
- threading, GPUs, SIMD intrinsics and batching in phases;
- background (eager) comparisons;
- speculative refinement at entry: testing a new denominator, entered or a result, against the base before it meets anything (Design 2; the form before the amendment of Oct 29, 2026);
- a record of which pairs have met (Design 2);
- recording about a result's denominator more than §8.3 gives: divisibility tests, new pieces formed from the operation's quantities, or facts added to a denominator the lookup finds (a meeting's refinement of its two operand rows is inside, §8.2);
- an index that limits which pieces a remainder is tested against (Design 2);
- caching residual products, cofactors or powers of pieces (Design 2);
- a list of the rows that use each piece (Design 2);
- cluster maintenance;
- integers wider than $w$, p-adic methods, BLAS, fast multiplication.

## 12. Instrumentation

### 12.1 Counts

In the counting build, the implementation MUST count, separately for each **phase** (entry, add, subtract, multiply, divide) and, within an operation, separately for its **core** (everything before `store`) and its **store** (lookup, append and the new denominator's structures):

| Counter | Counts |
| --- | --- |
| gcds | calls of the shared gcd, with a histogram of $\text{bits}$ of the larger operand (bins 0 to 64) and the sum of those bits (the **gcd work**) |
| divisions | exact divisions and divisions with remainder |
| multiplications | full-width multiplications |
| additions | full-width additions and subtractions |
| lookups | lookup searches and slot probes |
| scans | row entries walked in merges, pieces tested against a remainder in meetings, pieces tested by `absorb`, rows visited in splits |
| refinements | splits, pieces created, row entries rewritten, pieces pulled out of a remainder into its row |
| events | new rows stored with $u = 1$ and with $u > 1$, meetings, absorbs, and pieces queued by the extra refinement; same-index fast paths, new denominators, overflows |

**Counting rules.** The implementation MUST count the following cases in exactly this way, as every row of the joint build does:
1. **The sign.** Multiplying by the sign $s$ of $m_y$ in division is not counted.
2. **Repeated division.** "Divide rest by $q$ as many times as it goes" counts one division with remainder per attempt, including the final attempt that fails. `power(h, q)` (§8.3) counts one division with remainder per attempt it makes: none for $h = 1$, $k$ for $h = q^k$, and its successful attempts plus the failing one otherwise; it is counted under `store`, and only for a new denominator.
3. **The gcd.** A gcd counts as one gcd, entered in the histogram with its operand sizes. The subtractions, shifts and trailing-zero counts inside it are not counted as additions, divisions or bit routines.
4. **Index arithmetic and hashing.** Arithmetic on positions and on the small numbers $\nu_q$, and the hash of the lookup, are not counted as additions or multiplications. They are counted as lookups: one lookup search per hash computed, and one probe per slot read (insertions and re-placements on growth included).

*Amendment, Oct 28, 2026:* §4.3 item 5 requires every routine to count its calls, but the table above has no row for the bit routines. Their calls are counted in a further counter, **`bitops`** (library DEC-8; the trailing-zero counts inside the gcd are excluded by rule 3, and so is the instrumentation's own $\text{bits}$ for the histogram). `bitops` is **reported only**, with every other counter of this section (rule item 6); it enters no measure: not the gcd work, nor any verdict, band or flag.

*Amendment, Oct 29, 2026 (approved by the author, with §8):* the Design 2 rows count meetings in place of entry refinement. All of Design 2's refinement now falls in the core of addition, subtraction and division, and none in `store`. The library names its counters in its DECISIONS.md.

The counters MUST be readable at any time, and MUST be reset only by `create`.

### 12.2 Memory

`memory` MUST report, for every structure, the **used bytes** (entries times entry size, plus every per-row header) and the **allocated bytes** (capacity). The structures and their entry sizes at $w = 64$:

| Implementation | Structure | Used bytes |
| --- | --- | --- |
| Design 2 | numerators | $12N$ |
| Design 2 | denominators | $8D$ |
| Design 2 | lookup | $4S$ |
| Design 2 | base | $8C$ |
| Design 2 | exponent rows | $8 \times$ (row entries) + headers |
| Design 2 | remainders | $8D$ |

A per-row header MUST be counted at its real size and SHOULD be at most 16 bytes. **Bytes per rational** is the total used bytes divided by the number of stored values $N$. Allocated bytes per rational is reported beside it.

### 12.3 Timing

The harness times phases; the implementations hold no timers. The harness MUST time entry, operations and read-out separately, with a monotonic clock read only between calls, never inside one.

## 13. Correctness

### 13.1 Against an exact reference

Every stored value of every run MUST be read out and compared with an exact reference computed with arbitrary-precision rationals, independently of the shared integer routines: numerator and positive denominator, both in lowest terms, must be equal. Any mismatch fails the run for that implementation.

### 13.2 Invariants

`audit` MUST check, in the test build:

- **All:** every stored value is in lowest terms with a positive denominator; zero is $0/1$.
- **Denominators:** every denominator index is found by the lookup at its value; the lookup holds exactly $D$ indices and is at most half full; the denominator list has no duplicates.
- **Design 2:**
  - the base pieces are pairwise coprime and each greater than 1;
  - every row is sorted by piece index, with every $\nu \ge 1$ and every index below $C$;
  - every remainder is at least 1, and the known part times the remainder equals the denominator: $u_k \prod_q q^{\nu_q(K_k)} = d_k$.

`audit_changed` MUST make the same checks, restricted to what changed since the last audit (full or incremental):
- **All:** the values stored since then.
- **Denominators:** the denominators added since then, each found by the lookup at its value; the lookup's count and load.
- **Design 2:** each piece created (by `absorb` or a split) or rewritten (by a split) since then, against every other piece (greater than 1 and coprime to each: $C$ gcds per such piece); each row created since then, and each row rewritten since then by a split or by a meeting (its known part or its remainder), in full.

The test build records what changed in a change list that only the audits read; recording it MUST NOT change any result (§4.6 item 4).

*Non-normative: what the change-only audit can miss.* `audit_changed` checks only what the change list names. A fault that corrupts something outside it can pass: for example, a Design 2 piece corrupted to a value still greater than 1 and coprime to every other piece, without being recorded as rewritten, fails no coprimality check, and the rows that hold it are rechecked only if they changed. The full audit catches it, since it checks every row's known part times its remainder against its denominator. So the change-only audit is a quicker, partial check between full audits; the scheduled full audits of the gate (§13.3 item 2) remain the check of record.

### 13.3 Tests

1. Unit tests MUST cover: every worked example of the design note, with the stated intermediate structures; zero operands and zero results in every operation; negative numerators; division by zero; equal-index fast paths; a denominator of 1; an overflow in each operation; a composite piece in multiplication (the base $[6]$ case: the leftover stays in the remainder, and splits $6$ only when it meets row $6$) and in addition (a leftover at a piece of equal valuation); a remainder test that stays at a piece after dividing by it and after splitting it ($u = 12$ meeting the base $[6]$); entry computing no gcd against the base, a meeting that refines only what the operation needs, the extra refinement's counterexample of §8.2 item 3 (with it, $7/8$; without it, $14/16$, which the audit rejects), a result of addition and one of multiplication whose denominator the lookup finds, checked to make no power test, and a tested piece with $h = 1$, checked to cost no division.
2. **The gate.** Every job of the measurement rule MUST pass, in the test build and before any measured run, one complete run (entry, operations and read-out) audited on this schedule. Every call that stores a value counts: `enter` and the operations, so **entries are audited**, on the same schedule as operations.
   - a full audit (`audit`) after each of the first 200 calls of the job;
   - then a full audit after every 64th call (calls 256, 320, 384, …);
   - a full audit after the last call.

   Between full audits, the test build MAY run `audit_changed` after every call.

   **Large base (Design 2).** Once Design 2's base has more than **1,024 pieces** (approved by the author, Oct 28, 2026, as in the rule), every scheduled full audit except the one after the last call MUST check pairwise coprimality of the base only incrementally, and `audit_changed` MUST then run after every call: each piece created or rewritten by the call is checked against every other piece (§13.2). Every other check of those full audits is made in full, and the full audit after the last call is complete, the pairwise check included. So no full audit but the last takes more than $1{,}024 \cdot 1{,}023 / 2 = 523{,}776$ coprimality gcds, and every pair of pieces is still checked, when the later of the two was created or last rewritten.

   *Adapted Oct 29, 2026, with §8:*
   - pieces are created only in meetings, by `absorb` or a split, and change only by a split, so "created or rewritten by the call" means by the meetings of that call;
   - entry and multiplication create no piece;
   - rows rewritten by a meeting, in their known part or their remainder, are checked by `audit_changed` like rows rewritten by a split.

   *Non-normative:* on demand, the pilot's bases reached 3–64 pieces, against 2,400–3,200 in the eager form, so the pilot jobs do not reach this rule; it remains as a guard.
3. The 32-bit build MUST pass the unit tests.

*Non-normative: the gate's cost.* A job of $n_c$ calls gets about $200 + n_c / 64$ full audits: about 670 for the rule's 30,000-call jobs. Every full audit of Design 2 is linear in its structures (values, lookup, rows and remainders), a few milliseconds each, a few seconds per job, except the pairwise-coprime check, $C(C-1)/2$ gcds of pieces: 1.5 to 3 s at $C = 10^4$ (30–60 ns per gcd). Done at every full audit, it would cost 3 to 30 minutes on a job whose base reaches $10^4$ pieces or more; with the large-base rule above, it costs at most about 16–31 ms per full audit, and the incremental checks about $C^2/2$ gcds over a job, plus one complete check at the end: a few seconds per job, under 15 s at $C = 1.5 \times 10^4$. The rule's estimate gives the total over its run plan. These figures were made for the eager Design 2; on demand, its base stays far smaller (§13.3 item 2), and the pairwise check costs little.

## 14. Limits

Fewer than $2^{32} - 1$ stored values, denominators and pieces per class; exceeding them aborts (§4.5).

## 15. Choices not settled by the design note

Each item is a choice this specification makes where the note is silent or leaves room; each is local to the sections named. All are approved by the author, Oct 28, 2026, and are fixed before any measurement.

- **G-1** (§4.2, §5, §6). A zero result is stored as $0/1$ by `store`, as the note now states for addition; `store` then also sets $R$ to empty and $u$ to 1.
- **G-2** (§4.3). Numerators exclude $-2^{w-1}$; denominators are signed and at most $2^{w-1} - 1$.
- **G-3** (§4.3). No full-width intermediate wider than $w$; overflow of any intermediate is overflow, even when the reduced result would fit. The lookup hash is index arithmetic and uses unsigned 64-bit arithmetic at both widths.
- **G-4** (§4.3). The shared gcd is the binary method.
- **G-5** (§5). The lookup's hash multiplies the value by a fixed odd 64-bit constant (about $2^{64}$ divided by the golden ratio) and keeps the top $\log_2 S$ bits, rather than taking the value mod $S$, which clusters on denominators with many factors of 2; initial $S = 16$.
- **G-6** (§4.6). Three builds of one source; timing runs carry no counters.
- **D2-1** (§8.2). *As amended Oct 29, 2026, this applies to `absorb`, the only scan of the base, and to `reduce`, which stays at a piece in the same way.* `refine` made one scan of the base: it stays at a piece after dividing by it or splitting it, and never restarts at piece 0. The note's cost table agrees ("one scan of the base, at most $C + \tau$ gcds plus one per piece created by a split"); restarting at piece 0, as an earlier draft of the note did, is a plain inefficiency, removed at the author's direction (§15.1).
- **D2-2** (§8.2). A split refines $\{g, q/g\}$ by pair refinement; the new pieces are sorted increasingly, and the smallest keeps $q$'s index.
- **D2-3** (§8.3–8.6). Every operation with different indices reuses the valuations it knows and refines only the rest: multiplication (the rows added, less the cancellation), division (the valuations of $d_i / \gcd(d_i, d_j)$, $u = t/g_1$), and addition and subtraction (the maximum of the two valuations, less the cancellation). Where a cancellation is not a power of its composite piece, the leftover $q^n/h$ joins the result's remainder. *As amended Oct 29, 2026:* nothing is refined at `store`; $u$ also carries the operands' remainders (§8.3). Required under R-1 (§15.2).
- **R-1** (§7.4, §8.3, §10). **The author's ruling, Oct 28, 2026 (option 2).** Each design uses only the result reuse that its own structure gives for free: reuse is allowed only where it is **what the design's own production implementation would naturally do**. Design 2's reuse qualifies, because the valuations of a result's denominator are a direct output of its arithmetic, and only the unknown part is refined (D2-3). Design 1's eager copy of an operand's row into the result's row, residuals times $\mu$, does not, because a production version would more likely be lazy; it is removed (D1-3). The lazy and deferred forms are later improvements, outside the baseline (§10, §15.2).
- **D2-4** (§8.4, §8.6). The same-index paths of addition and division store the result's denominator with $R$ empty and $u = e$, since the cancellation $h = \gcd(t, d_i)$ is not split over the pieces; that of multiplication doubles row $i$, with $u = u_i^2$. *As amended Oct 29, 2026:* nothing is refined at `store` (formerly: refined from scratch).
- **D2-5** (§8.4, §8.5). Powers of pieces are formed by repeated multiplication; per-piece gcds in multiplication use the numerator as already divided.
- **D2-6** (§8.1). Row entries are two 32-bit fields, 8 bytes, as in the note's memory formula.
- **M-1** (§12.2). Bytes per rational uses used bytes, with allocated bytes reported beside it; per-row headers are counted.
- **I-1** (§12.1). Counts are split into entry and the four operations, and within an operation into core and store, so a result's entry cost is visible inside the operation. *As amended Oct 29, 2026:* Design 2's refinement falls in the core of addition, subtraction and division (their meetings); its `store` has only `finish` and `power`.
- **I-2** (§12.1). The counting rules: the sign is not counted; repeated division counts every attempt, the failing one included; a gcd counts once, its inner steps not at all; index arithmetic and the hash count as lookups, never as arithmetic.
- **T-1** (§4.1, §13.2, §13.3). The gate audits in full after each of the first 200 calls, then after every 64th call and after the last; entries count as calls. Between full audits an incremental audit MAY run after every call.
- **T-2** (§13.3). Approved by the author, Oct 28, 2026. Once Design 2's base has more than 1,024 pieces, the scheduled full audits before the last check pairwise coprimality only incrementally, with `audit_changed` after every call; the last full audit is complete.
- **D2-7** (§8.2). *Oct 29, 2026, approved by the author.* The meeting's queues are first-in, first-out; queue A is emptied before each piece taken from queue B; a queue never holds a piece twice; a split adds its new pieces to every queue that holds the split piece, taken or not; the remainders' gcd is taken only when both queues are empty.
- **B-1** (§10). The "outside" list of §10 adds to the note's list, so that builders cannot read these as allowed: SIMD intrinsics; caching cofactors or powers of pieces, not only residual products; a list of the rows that use each piece, which the note mentions only as absent from the skeleton; and integers wider than $w$. (Its items for Design 1 and the control are in the joint text.)

### 15.1 Plain inefficiencies removed

At the author's direction, the following repeated work, found in the procedures of the design note or of the earlier draft of this text, is removed. None changes a stored value, a structure or what is recorded; each removes only computation whose result was already known within the same call, could not change, or was not used. The note is in line with every item. Result reuse, formerly D2-c here, records more than before, so it is not a plain inefficiency; it is in §15.2.

- **D2-a** (§8.2; since Oct 29, 2026, `absorb` and `reduce`). `refine` no longer restarts at piece 0 after each division or split: one scan, staying at a piece after dividing by it or splitting it, testing again only pieces created by a split.
- **D2-b** (§8.2; since Oct 29, 2026, `absorb` and `reduce`). `refine` stops scanning as soon as `rest` is 1, instead of testing the remaining pieces against 1.
- **D2-d** (§8.2; since Oct 29, 2026, `absorb` and `reduce`). The gcd that the scan finds is used, not computed a second time ("find a piece with $\gcd(\text{rest}, q) \ne 1$", then "set $g$ to $\gcd(\text{rest}, q)$").
- **D2-e** (§8.4). Each power $q^a$ of an equal piece is formed once and kept with the piece, not formed again for the gcd.
- **D2-f** (§8.3–8.5). In addition, subtraction and multiplication, the test "$h$ is a power of $q$" is made after the lookup, by `finish`, and only for a new denominator, since its result serves only to build the new row; and $h = 1$ is recognized as $q^0$ with no division attempt.

### 15.2 Result reuse

Under the author's ruling R-1 (Oct 28, 2026, option 2), each design uses only the reuse that its own structure gives for free, the way a production implementation of that design would naturally do it, at a new denominator only, with no gcd. The note is in line with this item; Design 1's (D1-d, removed) is in [its specification](../08-common-divisors/v0.1.md#152-result-reuse).

- **D2-c** (§8.3–8.6). **Kept.** Addition, subtraction, multiplication and division with different indices pass the valuations their walk computed as $R$, and only the unknown part as $u$: the leftovers at composite pieces, or $t / g_1$ in division, and, since Oct 29, 2026, the operands' remainders. Multiplication with the same index doubles row $i$. It qualifies: the valuations are a direct output of the operation's own arithmetic, and a production coprime-base implementation would not throw them away.
